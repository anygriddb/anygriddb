# Migration plan

Historical: every phase below is done. This plan took the tree to the one the
[decision records](adr/README.md) describe.

Rules for every phase:

- **Each phase leaves the product working.** Lint, typecheck, unit tests,
  integration tests on PostgreSQL, and the end-to-end journey pass before a
  commit.
- **Each step is one Conventional Commit.**
- **Docs follow the code.** `TECH_STACK.md` and `ARCHITECTURE.md` describe
  what runs, not what is planned.

## Phase 1 — Reliable events and jobs (ADRs 0008, 0022, 0025)

Done (2026-11-07), XLSX isolation and its evaluation included (ADR 0025).
The product jobs keep their two-minute
lease: graphile-worker frees the job of a crashed process only after four
hours, and a person following an import must learn within a minute that it
stopped.

0. Extract the row write service (ADR 0022): tRPC and the REST API both
   call it, and row events leave from it alone. An integration test shows
   that a REST write marks dependent tables stale, which it does not today.
1. Add graphile-worker. Its schema is created by the migrations.
2. Enqueue row events in the write's transaction. Webhooks, notifications,
   and automations become tasks.
3. Move imports, exports, copies, and snapshots onto graphile-worker. The
   `jobs` table keeps progress and cancellation. XLSX parsing runs in an
   isolated worker with limits, after the library evaluation (ADR 0025).
4. Move schedules, webhook retries, and purges to its crontab and retries.
5. Remove `ag:events`, `JOB_WAKE`, and the homemade lease.

**Done when:** killing the API in the middle of a write loses no webhook,
and emits none for a write that did not commit (integration test).

## Phase 2 — Data layer (ADRs 0004, 0005, 0016, 0017, 0022, 0023)

Steps 1, 2, 4, 6, and 7 are done (2026-11-07).

- The runner adopts a database Drizzle migrated by checksum, or by
  Drizzle's journal date for a file edited since.
- UUIDv7 ids come from `ag_uuidv7()`, a SQL function built on
  `gen_random_uuid()` and set as the default of every id column, catalog
  and user tables alike. The application generates none: the database
  default covers every insert, raw SQL included, with no extension.
- Step 3 moves to phase 5. The interface between the read engine and a
  dialect is designed with its second implementation, MySQL, beside the
  PostgreSQL one, rather than guessed from one.
- Step 4 is done: `data_tables.storage` and `EngineTable.storage`, native
  for every table until sources exist.
- Step 5 waits for the feature that needs it, read-only SQL access to one
  base (`GRANT USAGE` on its schema). Until then a schema per base would
  touch every SQL builder for no visible gain, and nothing done meanwhile
  makes the move harder: tables move with `ALTER TABLE … SET SCHEMA`.
- Step 8 is done for rows, the writes several transports share. Catalog
  commands (fields, views, bases) have one transport, tRPC; they move to
  services when a second one needs them.

1. The SQL migration runner adopts the databases Drizzle already migrated.
2. Kysely with `pg`, and types generated by `kysely-codegen`. Rewrite the
   catalog access.
3. Rewrite the read engine as an intermediate representation plus a
   PostgreSQL backend, with the same behavior and the same tests. Field and
   row rules come along.
4. Add a storage per table (`native` or `external`) to the catalog and the
   engine. Only `native` exists so far.
5. Move each base's native tables to their own schema.
6. Generate UUIDv7 identifiers in the application.
7. Exact numbers as decimal strings in the core, typecast, display, and
   REST API (ADR 0023).
8. The remaining tRPC routers and REST handlers move onto services
   (ADR 0022).

**Done when:** Drizzle and `postgres` are gone, and every suite passes.

## Phase 3 — No Redis, files on disk (ADRs 0009, 0010)

Done (2026-11-07).

- Presence stays in each process's memory; its changes travel on the same
  `NOTIFY` channel as the rest of realtime.
- The automation rate limit is counted from `automation_runs`, so it holds
  across processes without a shared counter.
- RustFS comes as an overlay file, `docker/compose.s3.yml`, not a profile:
  a profile can add a service but cannot switch the API's storage to it.
- The compose file stayed on PostgreSQL 17 until phase 8, step 3, which
  moved it to 18 with its upgrade path.
- `anygriddb storage migrate` copies and never deletes, so it can run
  while the instance serves, and again after the switch. The orphan sweep
  only considers files older than a day, and keeps any kind of key it has
  no reference check for.

1. Realtime and presence through `LISTEN/NOTIFY`. Rate limits in memory.
   Cell locks in a table.
2. A storage interface with a disk driver (the default) and an S3 driver.
   Staged imports and job files go to storage.
3. `anygriddb storage migrate`, and a job that removes orphaned files.
4. The compose file runs PostgreSQL 18 and AnyGridDB, with an optional
   RustFS profile.

**Done when:** the default compose file has no Redis and no object store,
and attachments, imports, and exports work.

## Phase 4 — Web app (ADRs 0011, 0012, 0013, 0021)

Steps 1 to 4 and 6 are done (2026-11-07); step 5 comes with phase 5.

- Routes are declared in code (`apps/web/app/router.tsx`), not generated
  from files: fourteen routes do not need a code generator, and the tree
  reads in one place.
- `PUBLIC_URL` replaces `WEB_ORIGIN` and `PUBLIC_API_URL`, now one
  address; `WEB_ORIGIN` is still read in its place. The compose file
  publishes the image on port 3000, the address of the development server
  too.
- Share pages get `noindex` and no other meta tag: the name of a view
  behind a password must not show before the password.
- The React Compiler's lint rules found 21 errors. They are fixed: the row
  pages became an external store read with `useSyncExternalStore` (part of
  step 4), dialogs reset by mounting their form on open, and a share's
  password check is an event instead of query state. Only the grid itself
  stays uncompiled, as TanStack Virtual returns a mutable instance.
- Pages load with `React.lazy`: TanStack's `lazyRouteComponent` calls
  `use()` only while loading, which React reports. A failed chunk after a
  deploy reloads the tab once (`vite:preloadError`).
- Radix and dnd-kit are gone. The overlays keep their names in
  `packages/ui`, so the views changed little; a menu heading is now a
  section. Native `select` and checkbox inputs stay: they are already
  accessible. React Aria's date and number fields and its combo box come
  with the cell editors' rework (step 4).
- A kanban card has a drag handle for the keyboard; a calendar event moves
  by mouse, or by editing its date: a handle does not fit in a day cell.
- A second Playwright journey drives the menus, a submenu, the context
  menu, and a popover from the keyboard.
- Step 3, first half: error codes. One registry in `packages/core` holds
  every public error; a tRPC middleware sends an `AppError` thrown
  anywhere with its status, so no regular expression decides any more
  what people may read. Formula syntax errors, internal 500s until now,
  are public. A row lock is 409 on both transports. Webhook and
  automation outcomes ("Timeout", "Loop limit") stay stored labels, which
  the app translates as values.
- Step 3, second half: Lingui. A codemod moved 920 messages to macros with
  named placeholders, and the English dictionary into the English PO
  catalog. The conversion warning counts with ICU plurals. Literal braces
  in help texts became placeholders, as ICU would read them as arguments.
  Still to do: automation steps and webhook deliveries store a code like
  jobs do; until then the app resolves their stored text in one place.
- Step 4: the selection is a store read with `useSyncExternalStore`, each
  cell a component that reads its own flags; the grid component no longer
  re-renders when the selection moves, which matters as the React
  Compiler cannot compile it. Group and add-row lines are rows of the
  grid too. Cell editors keep native inputs for now: React Aria's date,
  number, and combo-box fields replace them one editor at a time.
- Step 6: the parser reports where an error is (`FormulaError`, a public
  AppError with a span) and tokenizes with positions, so the editor
  underlines the exact token. Two parts wait for phase 5, where they
  matter: a type checker apart from the SQL compiler (types are checked
  by the server on save), and marking the functions a source cannot run.
- Step 5, showing what a source or a rule forbids, is mostly about
  sources: it is done with them in phase 5.
- Found on the way: a field added or changed left the rows unread, so a
  new formula showed empty until a reload. The workspace now reads the
  rows again on a catalog change.

1. Vite, React Compiler, and TanStack Router. The API serves the built files
   on the same origin, with runtime configuration.
2. React Aria Components in `packages/ui`, then in the views.
3. Lingui catalogs, and error codes from the API.
4. The grid: selection in an external store, and the ARIA grid pattern.
5. The UI shows what a source or a rule does not allow.
6. A CodeMirror 6 formula editor on the shared parser and type checker:
   completion, inline errors, functions a source cannot run.

**Done when:** one image and one origin; keyboard and screen-reader checks
on the grid, the record panel, and the forms.

## Phase 5 — External sources, read (ADRs 0005, 0006, 0023, 0024, 0026)

Step 1 is done for PostgreSQL (2026-11-07): a source is saved only after
a connection over verified TLS succeeded, with the dedicated account it
will use; the password is encrypted and write-only, and audit snapshots
leave it out. The integration suite runs a PostgreSQL with a self-signed
certificate the test pastes, by name and by address. MySQL, MariaDB, and
SQL Server accounts are checked when their drivers arrive (step 3).

Step 2 is done for PostgreSQL (2026-11-07): introspection reads, from
pg_catalog and as the account sees it, the tables and views it may read
(partitions as their parent), their columns with the account's column
rights, enumerations as single selects, domains as their base type,
primary and foreign keys, and what the account may insert, update, or
delete (a right on one column counts). Types AnyGridDB cannot hold
exactly show as read-only text. Administrators preview it per source.

Exposing and reading are done for PostgreSQL (2026-11-07): an
administrator picks a source's tables for a base; their foreign keys
become links both ways, and their rows are read where they live, through
the same read engine as AnyGridDB's own tables, on a pool per source in
read-only transactions. Filters, sorts, search, links, formulas, and
totals run in the client's database; numbers stay exact. Exposed tables
are read-only (phase 6 writes), and comments on their rows live in the
control plane. An end-to-end journey declares a source, exposes two
tables, and reads them in the grid.

MySQL and MariaDB are declared, checked, and introspected (2026-11-07):
`mysql2` over verified TLS, accounts with global administrative grants
refused, the server's flavor checked against the engine chosen, and
information_schema read as the account sees it (`tinyint(1)` as a
checkbox, enumerations as single selects). Integration tests run MySQL
8.4 and MariaDB 11.4 with a self-signed certificate.

Their tables are exposed and read (2026-11-07), through the dialect seam
(`packages/core/src/query/dialect.ts`): rows, links both ways, filters,
search, sorts (option order included), groups, footers, and DATETIME in
the source's time zone, in read-only transactions under the source's
time limit.

Formulas run on them too (2026-11-07), held by a conformance suite that
reads the same 84 formulas over the same rows on PostgreSQL, MySQL 8.4,
and MariaDB 11.4 and requires the same results, with results pinned on
the reference. Making them agree fixed AnyGridDB's semantics: computed
numbers read canonical, division and AVERAGE round to 20 decimals, text
compares by code point, and instants add in UTC. SQRT, EXP, LN, LOG, and
POWER run in floating point on MySQL and MariaDB, rounded to 15
significant digits, and the field says so: an engine's limits are shown,
not refused (ADR 0027).

Lookups and rollups run there too (2026-11-07), in the same suite: a
list is ordered JSON built with GROUP_CONCAT, its joined text computed
where it is built, and a rollup aggregates the linked rows directly. A
mean divides as `/` does, text extremes compare by code point, and a
list's numbers read canonical, on PostgreSQL as well. A list of lists
and ARRAY_UNIQUE wait on MySQL and MariaDB.

**Decided deviation from ADR 0005.** The compiler does not build a
separate expression tree rendered through Kysely. It emits one query
shape and asks a dialect object for every construct engines spell
differently; the PostgreSQL dialect writes what the engine wrote before.
A tree would mirror the dialect's methods one for one, and Kysely would
only carry raw fragments, since AnyGridDB defines every function's
semantics itself. The ADR's goals stand: one backend per engine, results
identical or shown to differ (ADR 0027), and a conformance suite.

SQL Server is declared, checked, and introspected (2026-11-07): `tedious`
over TLS with the certificate verified, a sysadmin or CONTROL SERVER
account refused, SQL Server 2017 or later, and the catalog views read as
the account sees them, its rights from HAS_PERMS_BY_NAME. The
integration test runs SQL Server 2022 forcing encryption with a
self-signed certificate.

Its tables are exposed and read (2026-11-07) through a T-SQL dialect
(`packages/core/src/query/dialect-sqlserver.ts`): booleans are BIT
values that become conditions where T-SQL wants them, zones go to AT
TIME ZONE by their Windows names (CLDR's map), pages use OFFSET … FETCH,
links are JSON built with STRING_AGG and read with OPENJSON, and a row
comes back as one FOR JSON object. Reads run in tedious's own
transaction; SQL Server has no read-only one, so the dedicated account's
rights keep a read a read.

Formulas, lookups, and rollups run on SQL Server too (2026-11-08), in the
conformance suite: the 84 formulas, lookups, rollups, and list filters
read exactly as on PostgreSQL. T-SQL types a decimal by its operands'
declared types and stops at 38 digits, rounding or overflowing silently
past them; the compiler follows each number's `decimal(p, s)`
(`packages/core/src/query/digits.ts`), widens a dividend so that a
quotient keeps AnyGridDB's 20 decimals, computes a mean as a whole
quotient plus an exact remainder, and marks a field `precision` only
where the declared types can truly lose digits (ADR 0027). A date the
formula writes out is read when it compiles (`iso-instant.ts`) rather
than by SQL on every row: SQL Server refuses a query past a complexity
bound, and the parser written in T-SQL is long.

Nothing an engine can compute is refused any more (2026-11-08): list
functions, lookups of lists, ENCODE_URL_COMPONENT, lower-case am/pm, and
the footer median run on MySQL, MariaDB, and SQL Server, in the
conformance suite. MySQL needs 8.0.14 (derived tables that read the
outer row, and LATERAL).

1. Declaring sources: administrators only, a host allow list, a dedicated
   account, verified TLS with a pasted certificate when needed,
   administrator accounts refused, and encrypted, write-only credentials
   (ADR 0026).
2. Introspection for PostgreSQL, MySQL/MariaDB, and SQL Server; foreign keys
   become links; the account's privileges per table decide what can be
   written. Read MikroORM 7's introspection (MIT) first.
3. MySQL/MariaDB and SQL Server backends for the engine. The conformance
   suite runs on Testcontainers for each engine, over verified TLS.
4. Estimated totals, per-query time limits, connection limits, and read
   replicas. Done but replicas (2026-11-07): a client table read whole
   shows the total its engine's statistics estimate past 10,000 rows, and
   the grid counts exactly on demand; a count that runs past the time
   limit falls back to the estimate; later pages read without a count.
5. Exact numbers from every driver; values at the limits in the conformance
   suite (ADR 0023).
6. A guide per engine: the account script, its `GRANT`s, and how to enable
   TLS (ADR 0026). Done: [`docs/sources.md`](sources.md) (2026-11-07).
7. Oracle, when it comes: review `kysely-oracledb`, or write our own
   compiler (ADR 0024).

## Phase 6 — External sources, write and enrich (ADRs 0006, 0007)

Step 1 is done (2026-11-08, ADR 0028): an administrator enables editing,
adding, and deleting rows per exposed table, within the account's rights
read again at that moment. A change locks its rows, compares each field
with what the person saw, and is refused when one moved; the grid then
shows the current value. Values go back in each column's own type, and
what the engine refuses is said plainly. Every write is recorded in three
steps in append-only tables, its row events queued with `applied`, and a
job confirms applied writes and settles intents a crash left open. The
conformance suite runs the same writes on PostgreSQL, MySQL, MariaDB,
and SQL Server and requires the same results, conflicts, refusals, and
trail. Statuses, signatures, the row trash, imports, automations, and
inverse links stay with AnyGridDB's own tables for now.

Step 2 is done (2026-11-08, ADR 0032): fields people add to a client's
table live in a side table, in a schema of the client's database its DBA
gives AnyGridDB, keyed like the client's table and joined to it on read.
They are edited even where the client's table is read-only, filter,
sort, group, and feed lookups like any column, and follow writes in the
same transaction. Tried on the four engines; the conformance suite
requires the same results on each. A control-plane fallback, when no
schema is granted, is left for later.

Step 3 is done (2026-11-08, ADR 0031): an administrator watches an
exposed table by a column the database sets on every change (a date and
time, read again two minutes behind for late commits, or a `rowversion`)
or by SQL Server's Change Tracking. A job checks it on its interval from a
cursor; open grids read the changed rows again, and webhooks and
automations receive row events from the source `external`, once each,
without AnyGridDB's own writes. Runs and deliveries now name a client's
row by its key. Tried on the four engines with an ERP of 20,000 orders: a
grid shows another application's change within seconds.

Step 4 is done (2026-11-08, ADR 0033): statuses and signatures on a
client's rows, read-only tables included, kept in AnyGridDB's database by
the row's key. Locking seals the row's stored values with their SHA-256;
a write reads the status again once its intent is recorded, and a lock
waits for the writes recorded before it, so none lands unsealed. A job
compares sealed rows every five minutes, and a watched table's changed
ones at once; a change is marked in the grid, told to those who locked
or signed and to the owners, and blocks signing until an owner locks the
row again. The conformance suite runs it on the four engines; the lab
shows a change made in each ERP within six seconds. The status and
signature buttons, lost from the web app in the rebuild of 2026-11-07,
are back in the row's panel for both storages.

Step 5 is done (2026-11-08, ADR 0034): a client's table can be read from
a copy in AnyGridDB's database, refreshed every N minutes. The copy keeps
each row's id from the client's engine, so views, comments, statuses,
and links survive a change of mode. A refresh pages through the client's
table with foreign keys read raw, loads a new copy beside the current
one, compares them, and swaps them in one transaction; added, changed,
and deleted rows reach grids, webhooks, and automations. The conformance
suite requires the copy to read exactly as the live table on the four
engines; in the lab, 60,000 order lines copy in 2 to 10 seconds.
Found on the way: a grid whose first page failed asked again in a loop
(150,000 requests, then the rate limit); it now waits for "try again".

1. Writes that detect conflicts, with an audit in three steps and a job
   that settles open entries.
2. Enrichment fields: a side schema in the client's database, or the
   control plane when no schema is granted.
3. Detecting changes made elsewhere (a modification-date column, SQL Server
   Change Tracking). This feeds realtime, webhooks, and automations.
4. Fingerprints of signed rows, with scheduled checks and alerts.
5. Synced mode per table.

## Phase 7 — Rules and dashboards at scale

Step 1 is done (2026-11-08): field and row rules already compiled through
the dialect seam since phase 5; the conformance suite now holds them on
the four engines. A row rule keeps its rows only, totals and aggregates
included; a hidden field reads, filters, and counts as empty; writes to a
read-only field or to a row outside the rule are refused. It found that
SQL Server counted every aggregate `count(*)` as 1: FOR JSON's subquery
evaluated it once per row read. Aggregates are now computed in a derived
table on every engine, and made JSON only then; footer counts joined the
suite.

Step 2 is done (2026-11-08, ADR 0035): charts read one aggregate per
group of up to two fields, computed by the engine the rows live in under
the reader's rules, and draw with ECharts: columns, horizontal bars, a
line, an area, or shares of the total, stacked when the measure adds up,
with a validated palette in both themes and a table view. The
conformance suite holds the groups and values on the four engines.
Found in the lab: a dashboard of five widgets was answered 414, as
Fastify capped tRPC's batched path at 100 characters.

1. Field and row rules compiled for external sources.
2. Dashboards on Apache ECharts, with aggregates computed by the source.

## Phase 8 — Operations

HTTPS only, ahead of this phase (2026-11-08, ADR 0029): the API serves
TLS on its one port, plain HTTP there gets a redirect, and without the
operator's certificate the instance makes its own name-constrained
authority, with sealed keys and renewal without restart. Cookies are
`__Host-`; the compose file no longer publishes PostgreSQL. Every
connection AnyGridDB opens is encrypted and verified too (ADR 0030):
PostgreSQL and RustFS in the stack get certificates from an internal
authority, and settings that would connect in clear stop the start.

Step 1 is done (2026-11-08, ADR 0018): `/metrics` for the operator's
token only, and OpenTelemetry spans to a collector over TLS when one is
named. Tried in the lab against a local collector: requests, procedures
under their request, source transactions, and tasks arrive as spans.

Step 2 is done (2026-11-08): besides the conformance suite, which runs
the four engines in CI, a browser journey on a client's table edits a
row, locks it, sees signing refused and the change found once another
application moved it, signs it once locked again, reads the table from
a copy, and charts it on a dashboard. Found on the way: a refused
signature left its dialog open over an inert page; it now closes, but
for a mistyped password.

Step 3 is done (2026-11-08): the compose file runs PostgreSQL 18 on a
volume of its own. `scripts/upgrade-postgres.sh` moves a 17 stack's data
with a PostgreSQL 17 of its own, keeping the old volume. A one-shot check
refuses to start an empty 18 in front of 17's data, so `git pull` and
`up` cannot hide it. `scripts/backup.sh` and `scripts/restore.sh` cover
the database, files, and authorities with their sums.
`compose.managed.yml` runs AnyGridDB on a PostgreSQL of one's own over
verified TLS. [`docs/operations.md`](operations.md) has the offline
install too. Each was tried on an isolated stack: an upgrade from 17
with its data intact, a fresh install, a backup restored after damage,
and a TLS PostgreSQL 18 standing for a managed one.

Step 4 is done (2026-11-08): the README now starts from client
databases. Every table is a real SQL table, in AnyGridDB or in the
client's own database, read and computed where it lives.

1. `/metrics`, OpenTelemetry off by default.
2. End-to-end journeys in CI for native and external tables.
3. Offline install guide, backup guide, managed PostgreSQL guide, and the
   move of the compose file to PostgreSQL 18 with its upgrade steps.
4. README positioning: every table is a real SQL table, in AnyGridDB or in
   the client's own database.
