# 0003 — AnyGridDB's own store is PostgreSQL only

- Status: Accepted
- Date: 2026-11-07

## Context

Some clients ask whether AnyGridDB could store its own data in their MySQL,
MariaDB, or SQL Server. The control plane relies on PostgreSQL:

- **Triggers.** The audit trail, locked and signed rows, and the status
  workflow are enforced in PL/pgSQL triggers (`audit_record()`,
  `ag_stamp()`). Transaction-local settings (`set_config(..., true)`) carry
  the audit context.
- **Transactional DDL.** Adding or converting a field changes the table, the
  catalog, and the audit trail in one transaction. MySQL and MariaDB commit
  implicitly around DDL, so a failed conversion would leave the table and
  the catalog out of step.
- **Queues and realtime.** graphile-worker (ADR 0008) and `LISTEN/NOTIFY`
  (ADR 0009) only exist on PostgreSQL.
- **Formulas.** On another engine the same formula would return a different
  result. `7/2` is 3 in PostgreSQL and SQL Server but 3.5 in MySQL, and
  MySQL's default collation finds `'é' = 'E'`.

## Decision

- AnyGridDB stores its own data only in PostgreSQL.
- The image ships PostgreSQL 18; PostgreSQL 17 is the oldest version
  supported, because managed services lag.
- A managed PostgreSQL is supported (Azure Database for PostgreSQL, Amazon
  RDS, Google Cloud SQL, Scaleway, OVH, and others).
- The database needs one role that owns one database. No superuser and no
  extension are needed: the migrations and graphile-worker create neither.
- AnyGridDB needs a direct (session) connection. Transaction-mode poolers
  (PgBouncer, Supabase's or Neon's pooled endpoints) break `LISTEN/NOTIFY`
  and the session locks of migrations. The API checks the connection at
  start and refuses a pooled one with a clear message.
- Identifiers are UUIDv7, generated by the application.
  PostgreSQL 17 has no native `uuidv7()`.
- Other engines are external sources (ADR 0006), never the internal store.

## Consequences

- A few clients refuse PostgreSQL on principle; we lose them.
- Audit, signatures, and formulas behave the same on every instance.
- PostgreSQL 19 (general availability planned for November 2026) is adopted
  in the image after its first minor release.

## Rejected

- **MySQL, MariaDB, or SQL Server as the internal store.**
  - Every feature and every test would multiply by the number of engines.
    A multi-engine product carries thousands of lines of per-engine
    function mappings.
  - Comparable products that compile formulas to SQL store their own data in
    PostgreSQL only. GitLab dropped MySQL in 2019 for the same reasons.
  - SQL Server is proprietary. The open source policy allows connecting to
    it, not building on it.
- **SQLite as an embedded control plane.** It has no multi-instance writes,
  no `LISTEN/NOTIFY`, and native tables need PostgreSQL anyway.
