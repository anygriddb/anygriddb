# AnyGridDB architecture

The product is a Turborepo / pnpm workspace.

## Shape

```text
browser ──► one origin: the app (apps/web, built by Vite), tRPC,
              │          REST /api/v1, MCP /mcp, WebSocket, file routes
              ▼
           apps/api (Fastify) ── graphile-worker: row events, webhooks,
              │                   automations, notifications, schedules
              │                ── product jobs: imports, exports, copies, snapshots
     ┌────────┼──────────────┐
     ▼        ▼              ▼
 packages/  packages/db    file store: a directory (default) or any S3
 core       (Kysely, pg)   attachments, thumbnails, exports, staged uploads
              │
              ▼
         PostgreSQL 18 ─── one physical table per user table, the catalog,
                           the job queue, realtime (LISTEN/NOTIFY), locks
```

What each package owns, and where a change usually goes, is the table of
[`CONTRIBUTING.md`](CONTRIBUTING.md#where-to-change-what).

## Data model

- **A user table** is a PostgreSQL table named by `physical_name`. Each has `id`, `ag_status`, and system columns `ag_seq`, `ag_created_at`, `ag_updated_at`, `ag_created_by`, `ag_updated_by`, filled by the `ag_stamp()` trigger, and `ag_position`, the row's place in the table's order: rows are read by place, then by sequence, and a row put between two others takes a number between theirs (ADR 0060).
- **Columns** have a stable `name` (the physical column and the API key) and a `label` shown to people. Links are a foreign key, with its index (one-to-many), or a junction table (many-to-many); a two-way link adds an inverse column on the other table that shares the same storage.
- **Computed fields.** Formulas, lookups, rollups, link labels, and buttons have no physical column. The read engine in `packages/core/src/query` compiles the page payload into one bound query (`buildReadRows`), so they filter, sort, group, and aggregate in that SELECT. Counts, group stacks, footer aggregates, and comment badges are separate bound queries on purpose. A computed field over a table the reader cannot read compiles to null.
  - Formulas mean the same on every engine (ADR 0005), held by the conformance suite (`apps/api/src/sources/conformance.integration.test.ts`): computed numbers are exact and read canonical (`14.5`), division and AVERAGE round to 20 decimals, text compares by code point, and instants add and subtract in UTC, the reader's zone applying where a formula reads a wall clock.
  - Formulas read text as a date by AnyGridDB's grammar, the same on every engine (ADR 0005): ISO 8601, a date with an optional time and zone (`Z`, `±HH`, `±HH:MM`); text without a zone is in the reader's time zone, and anything else, a day that does not exist included, is blank.
- **Audit.** Every row write runs in `withAudit`: one transaction that sets `anygrid.user_id`, `anygrid.table_id`, the reason, and the source. The `audit_record()` trigger appends the old and new row to `audit_events`, refuses changes to `locked` or `signed` rows, and enforces the status workflow.
  - `audit_events` and `row_signatures` are append-only for everything the application does: nothing it runs rewrites them but an account's erasure, which changes the author alone, and nothing it runs deletes from `audit_events` but its own purge, once an administrator chose how long the trail is kept (ADR 0069). A signature is never deleted. This protects the trail from the application, not from whoever holds its PostgreSQL account, which owns these tables: guard that account as you guard the data.
- **Sources in the audit trail**: `web`, `api`, `import`, `template`, `duplicate`, `restore`, `trash`, `form:<share>`, `snapshot`, `automation:<id>`, and `retention` for the trail's own purge.
- **Trash.** Deleting a base, table, field, or view sets its `deleted_at` and keeps its storage. Every catalog read goes through the `live*` predicates in `apps/api/src/data/live.ts`, so the item disappears everywhere: sidebar, engine, REST, shares, realtime channels, schedules. A table takes the link fields of other tables that point to it into the trash (`deleted_with`), and a two-way link takes its other side; they come back with it.
  - A field read by a formula, lookup, or rollup cannot be deleted, and one that would not compile cannot be restored. A trashed field keeps its name, so a new field gets another one, and views keep their references to it: reads leave them out, a restore brings them back. A restored table or field whose name was taken meanwhile becomes "Name (2)".
  - After the days the instance keeps them (`trashDays`, 30 by default, a week to a year), a daily system job purges the item for good, audited under whoever deleted it; managers can purge earlier.

## Contracts

### The app

- **One origin.** The API serves the built app on its own origin (ADR 0011): every call from the browser is a relative URL, so there is no CORS, the session cookie is first-party, and nothing about the address is fixed at build time.
  - Page paths get `index.html` with `script-src 'self'` and `connect-src 'self'` (no inline script, no nonce); hashed files under `/assets` are cached for a year, and go out as the Brotli or gzip copy the build left beside them; any other answer of 1 KiB or more is compressed as it leaves (`apps/api/src/compression.ts`), request bodies never unpacked; share and invitation pages carry `noindex`, and never the name of what they share. In development, Vite serves the app and forwards the API's paths to it, so the browser sees one origin there too.
- **Dialogs, popovers, menus, and tooltips** are React Aria Components (ADR 0012), in `packages/ui`: focus moves into an overlay and back to its trigger, the page behind a modal is inert, menus take arrow keys and type-ahead, and a tooltip's trigger must be focusable.
  - Two things keep the browser's own `title` instead: text that is cut short or only decorates (a file name, a status, a fingerprint), which nothing can focus, and a control drawn once per cell or per pin, where a tooltip each would cost the grid its speed. Kanban cards move between columns by mouse or from the keyboard, with a drag handle; calendar events by mouse, or by editing the date.
- **Messages** (ADR 0013, source language ADR 0041) are Lingui macros with **English** as the source language; `pnpm --filter @anygriddb/web i18n:extract` writes the PO catalogs in `apps/web/locales`, and CI fails when they lag behind the code or French translations are incomplete. A language loads its catalog when it is chosen, before the first render.
  - Server errors are translated from their code (`apps/web/lib/errors.ts`); values the server sends, such as webhook outcomes, row statuses, and template names, from a closed list (`lib/known-text.ts`). System mail uses `apps/api/src/mail-i18n.ts` with the instance locale.
- **The grid** is a DOM grid with the ARIA grid pattern (ADR 0012): focus stays on the grid, which names its active cell with `aria-activedescendant`; cells carry their row and column indexes, `aria-selected`, and `aria-readonly`; numbers are row headers.
  - The selection (active cell, range, edited cell, fill) lives in a store outside React state (`components/grid/selection.ts`); each cell reads only its own flags, so moving the selection re-renders the cells whose look changes, not the grid. Rows load into another external store (`use-rows.ts`), page by page as they scroll.
  - A grouped grid's first page also says where each group starts (`buildGroupCounts` with `starts`, which numbers the view's rows in the read's own order), so its headers are placed before the rows under them are read (`group-layout.ts`); a grouped read orders rows whose group values sort alike by their key, so each group's rows follow each other.
  - A gallery reads its cards the same way, page by page as they scroll; a map reads only the rows that have a place, up to 5,000 (`map-places.ts`). A view setting is read first with its value kept locally, then saved: the rows read stay as long as what the read asks for is the same (`readKey`).
- **The formula editor** is CodeMirror 6 on the parser the server runs (`packages/core/src/formula.ts`): it highlights the tokens, completes `{fields}` and functions with their arity, and underlines a parse error where it is, with the message also in a status line a screen reader hears. The server checks the types when the field is saved. The editor's code loads with the first formula.
- **Routes** are typed (TanStack Router): a link to a page that does not exist, or a search parameter of the wrong shape, is a compile error. Each page loads its own code. The React Compiler memoizes components. It leaves a component it cannot follow as written, and the build does not say so: its lint rules run in CI, and a test keeps the list of the components and hooks it leaves out (`apps/web/lib/react-compiler-left-out.txt`), so one more is an error, not a silent slowdown.
- **Dashboards** belong to a base. Widgets are `metric` (one aggregate, or the value a field holds in the row that comes last by another field: one read of one row, sorted downward, the rows that tie taken last made first), `chart` (one aggregate per group of up to two fields, from the read engine's `buildGroupAggregates`, drawn with ECharts in `components/dashboards/chart-view.tsx`, ADR 0035), or `view_embed` (the first rows of a collaborative view, with the fields it shows, under its filter and its sort). Data is read with the caller's rights, field and row rules included, and optional view filters. A widget follows its table's channel and reads again once per burst of changes (`useTableChanges`).

### The API

- tRPC is the TypeScript contract; Zod schemas live in `packages/core`.
- **Errors** (ADR 0013): every error people may read is an `AppError` from `packages/core/src/errors.ts`, with a stable code, an optional detail (a field, a function), its HTTP status, and an English message. tRPC sends `{ code, detail }` in `data.reason`; REST, file routes, and job records carry `code` and `detail` next to the English `error`. Anything else is internal: the client learns `internal_error` and the log keeps the cause. The web app translates the code, never the message.
- **Exact numbers** (ADR 0023): a number field, and every computed number (formula, lookup, rollup, sum, mean, extreme), travels as a canonical decimal string, in the grid, REST, webhooks, and exports, so no value rounds through a float. Ratings, durations, and auto numbers stay JSON numbers. Typecast keeps the digits that were typed, reads a comma by the language it was told, and refuses what reads two ways; a JSON number is accepted and read as the decimal it prints as, except an integer past 2^53, already rounded, which is refused. Display formats the string with `Intl.NumberFormat`, which reads it exactly; only charts and map pins convert to a float.
- **REST**: `/api/v1` with record batches of 100, `typecast`, field keys by name or label, and `/bases/:id/openapi.json`. It takes a token, or the session on this origin (the API page tries requests with it).
- **MCP** (ADR 0040): Streamable HTTP at `/mcp`, stateless, a bearer token only (never the session), a browser's request from another origin refused. Its tools are the REST record plane; both read and write through `apps/api/src/public-api/`. A read-only token is offered the reading tools only. No language model is embedded.

### Row writes and client tables

- **Row writes** go through `apps/api/src/services/rows.ts`, whatever the transport: tRPC, REST, MCP, automations, public forms (ADR 0022). The service checks writable fields, rows in scope, link targets (an inverse one-to-many link needs write access to the other table), attachment ownership, and change reasons, then announces the change once. Transports parse input and present results; they hold no write logic.
  - Rows that set the same fields are inserted in one statement, in their order, and the rows of an update are locked together, in the order of their ids. An update that says what its author saw is compared under that lock, field by field, with the rows read again through the read engine, and refused when a value moved (`sameAsSeen`, ADR 0103).
- **A deleted row** keeps its many-to-many links, from every junction it sits in (its own links, and links from other tables that point to it), in an internal audit event written in the delete's transaction (`__ag_m2m`, hidden from row history). Restore rewrites them for rows that still exist; an older event from an earlier deletion is ignored.
- **Writes to a client's table** (ADR 0028) go through the same service, then `apps/api/src/sources/writes.ts`: enabled per table (edit, add, delete) by an administrator, each column per the account's rights. Rows are locked, read again, and compared with what the writer saw; statements come from `packages/core/src/query/external-write.ts`, in each engine's types. Each write is recorded in `external_writes` and `external_write_steps` (intent, applied, confirmed), append-only; the `external_settle` job confirms and settles them.
- **Synced tables** (ADR 0034, `apps/api/src/sources/sync.ts`, `packages/core/src/query/sync.ts`): a copy in the `ag_sync` schema of AnyGridDB's database, refreshed by the `external_sync` job, which pages through the client's table, loads a new copy beside the current one, compares them by `ag_id` (the row's id from the client's engine), and swaps them by renaming in one transaction.
  - The engine reads a synced table as PostgreSQL (`ExternalRelation.synced`); `storeOf` keeps every join in one database, so a link between a copy and a live table reads empty. Writes are refused; a copy is dropped a minute after the table is read live again.
- **Statuses on a client's rows** (ADR 0033, `apps/api/src/sources/statuses.ts`) live in `external_statuses`, named by the row's key, with the same workflow and roles as `ag_status`. Locking seals the row: its stored fields in a canonical form (`packages/core/src/query/seal.ts`) and their SHA-256.
  - A write reads the row's status before anything and again once its intent is recorded; a lock commits the status, waits for the writes recorded before it, then reads the row, so no write lands unsealed. The `external_seals` job (every five minutes, and at once for the rows a watch finds changed) compares sealed rows with the client's database, marks and notifies a change (`row_changed`), and records it. `external_status_events` is the append-only trail; `row_signatures` records the fingerprint signed.

### Access

- **Roles**: owner, editor, commenter, viewer. A table role overrides the base role. A role given to an address is an invitation, whether or not the address has an account, and the answer is the same in both cases, so that inviting an address does not tell who has an account.
  - An account's address being proved (ADR 0058), its holder finds the invitation on their home page and accepts or declines it there (`listInvitationsFor`, `answerInvitation` in `apps/api/src/data/sharing.ts`); an address without an account opens the mailed link. Only someone already in the base changes role at once. API tokens carry an optional base list and a read-only flag; the effective right is the lower of the token's and the user's.
- **Field and row rules**: `table_acls` and `column_acls` restrict a collaborator below their role; owners ignore them. With column rules, a field they do not name is hidden, so a field added later stays hidden until a manager opens it.
  - Every read on behalf of a person builds its engine with `readerEngine` (`apps/api/src/data/acl.ts`), and the read engine enforces the rules wherever a table is read: a hidden field compiles to empty in the page, formulas, lookups and rollups from other tables, filters, sorts, search, groups, and aggregates, and is left out of responses and the catalog; a row rule is AND-ed into every read of its table, links and rollups included, and reads the real values even of fields the reader cannot see.
  - A rule that no longer compiles keeps no row. This covers the grid, REST, exports, dashboards, webhook payloads, automations, and public shares (which read as their creator). Writes must name writable fields and target rows inside the rule (updates, deletes, links on both sides, statuses, signatures, comments, history). Collaborators with rules cannot use the row trash.
  - An import under a row rule writes what stays inside it and refuses, on its line, a row it would create or leave outside, and a key that finds a row outside it. Rule changes are audited like roles; revoking a member removes their rules. `catalog.viewAs` shows a manager what one collaborator reads, through the same engine.

### Sign-in and connections

- **Session cookie**: `__Host-`, `HttpOnly`, `Secure`, `SameSite=Strict`. A write or a socket that carries it comes from the app's own pages: the `Origin` a browser gives is `PUBLIC_URL` or the address the request was sent to, or the request is refused before anything reads it (`foreignSessionWrite`, `http.ts`), so a page of the same site on another name or port cannot use the session.
  - A session slides by its idle window while used and ends at its lifetime: 15 minutes and 12 hours by default, as the instance sets them (ADR 0043). Every sign-in path goes through `createSession`, which refuses disabled accounts.
- **Passwords**: Argon2id, 64 MiB. Past the instance's first account, a password sign-up makes no account until its address is proved (ADR 0058): `signup_requests` keeps it and a link is mailed to the address; the account is made when the link is opened with the same password, or at once from an invitation to that address. Every account's address is thus proved, and what trusts an address (`ADMIN_EMAILS`, a role by address, SSO and SCIM matching) needs no check of its own.
  - TOTP secrets: AES-256-GCM. Passkeys: WebAuthn. Deleting one's own account asks the proof a sensitive action asks (`apps/api/src/auth/erase-proof.ts`): the password, a code from the authenticator or a backup code when the account has one, and, where neither can be asked (no password, or a passkey for only factor), a sign-in less than ten minutes old. A wrong one counts toward the lock, a locked account takes no guess, and an API token is refused. Creating or administering a base needs a second factor.
- **Single sign-on.** OIDC goes through `openid-client`: an HTTPS issuer whose metadata names itself, PKCE, a nonce, and a state kept server-side, used once, and taken only from the browser that started the sign-in (a `__Host-` cookie whose hash the state keeps; SAML's relay state likewise). A sign-on binds the account to the provider's subject (`sso_identities`: OIDC `sub`, a persistent SAML NameID) and later finds it by that subject, whatever the address says.
  - The first time, the address finds the account: one the provider marks unverified is refused, and so is a different subject bringing the address of an account a provider still set up already holds (`auth/sso.ts`, ADR 0114). A SAML provider that sends only transient or address NameIDs keeps matching by address, on an account nothing holds. An account reached by its address proves its own factor first, whatever `ssoMfa` says, and a first binding is written only with the session that proof opens (`bindAfterProof`).
  - A session remembers the provider that opened it and never outlives the end a SAML assertion sets. The ID token's signature is checked against the provider's published keys, a SAML assertion that names a recipient must name this service, and OIDC Back-Channel Logout ends the sessions a provider names (`auth/oidc-logout.ts`).
- **HTTPS only** (ADR 0029, `apps/api/src/tls/`): the operator's certificate (`TLS_CERT_FILE`, `TLS_KEY_FILE`, reloaded when the files change), or one from the instance's own authority in `TLS_DIR`: ECDSA P-256, name-constrained to the instance's names, keys sealed with `AUTH_ENCRYPTION_KEY`, the server certificate renewed a month before it ends. The first byte of a connection tells TLS from plain HTTP, which gets a redirect on the same port. `/tls/authority.crt` serves the authority to install; Administration > Health shows its fingerprint.
- **Connections AnyGridDB opens** (ADR 0030): TLS, verified, beyond the loopback; `readEnv` refuses a `DATABASE_URL`, `S3_ENDPOINT`, or `SAML_ENTRY_POINT` that would not be, and SMTP requires TLS. The compose stack's one-shot `certs` service (`anygriddb tls services`) issues PostgreSQL and RustFS their certificates from the instance's internal authority, name-constrained to their names; PostgreSQL's `pg_hba.conf` takes network connections over TLS only.
- **The first account and the way back** (ADRs 0080, 0082). The instance's first account administers it, and is made with a token only `anygriddb install-token` gives, once, for an hour. When no administrator can sign in, `anygriddb admin recover` makes an account an active administrator and prints a link that sets its password, once, within the hour; each change it makes is on the sign-in trail as made from the command line.
- **A code by email** is a second factor for anyone but an administrator, where mail is set up (ADR 0085).

### Realtime, events, and automations

- **Realtime** (ADR 0009): clients subscribe to table, base, and their own user channel. Messages carry row ids, never values; clients re-read with their own rights, once for a burst of changes. Each socket's messages are handled in order. The hub keeps the sockets of each channel, so a message goes to its channel's sockets without looking at the others.
  - A socket is closed (4401) when its session ends: when it next speaks, and, for one that sends nothing, at the heartbeat, which asks in one query which of the open sockets' sessions are still live. Processes share messages through PostgreSQL `LISTEN/NOTIFY` on one channel: messages published in the same tick go out in one statement, each under PostgreSQL's 8,000-byte limit (row ids in chunks of 150).
  - What a socket follows is held to the rights its account has now: every process asks again in one grouped question at each heartbeat, and at once when any process says rights changed (a message on the bus that names no one). A channel no longer allowed is left, and its page told to read again. A reader under a row or field rule hears that a table moved, never which row or field. A socket is closed past 1 MiB of unread messages (1013), a pong counts only if it answers the ping under way, and an account holds 64 sockets per process.
  - The listening connection reconnects on its own; tabs subscribed meanwhile get a `stale` message and re-read. A tab also re-reads each channel after its own link was lost, once subscribed again (ADR 0049); the server pings every socket every 25 s and cuts the silent ones, and a tab that hears nothing for 65 s opens a new link. Cell edit marks and button presses take short leases in the `ephemeral_locks` table (unlogged: a crash clears them, which is what a lease wants).
- **Events** (ADR 0008): a row write queues one graphile-worker job, `row_events`, inside its own transaction, so an event exists if and only if the write committed. The job reads the transaction's audit entries (`audit_events.xact_id`) and hands each row event to the consumers its table has, one job each, added in one statement: webhooks (an active one), assignment notifications (a user field that notifies), automations (one switched on). A table with none queues nothing more.
  - Each consumer commits its own outcome with the jobs it starts (deliveries and their attempts, filter state and automation runs), so a retried job never sends twice. An import sends one `import` event: each batch replaces the queued event with its running count. Bulk catalog writes (field conversions, copies, templates, snapshots) send no row events. Realtime notices go out after commit and are not part of this guarantee.
- **Webhooks**: payloads may include the row's values, read with the creator's current rights. Deliveries are logged, retried after 1, 5, and 30 minutes (each attempt is a job keyed by delivery and attempt number), and a webhook switches off after 10 failures in a row. A sweep every ten minutes queues again a pending delivery whose attempt is long overdue. Outgoing requests check the resolved address inside the socket's own DNS lookup, so private and internal addresses are refused even under DNS rebinding.
- **Automations** run as their author, with the author's current rights, and audit their writes with the automation's name as the reason. They ignore their own writes, stop at depth 3, and start at most 300 runs a minute each. Past that a run waits (ADR 0115): it takes a place in a later minute from a count kept per automation in `automation_run_pace`, moved in one statement so the limit holds across processes, and is dropped with a notice to its author only after a day of waiting. A run is a job tried once: actions send mail and call URLs. Schedules run from graphile-worker's crontab every minute and are claimed with `FOR UPDATE SKIP LOCKED`.
- **A script in an automation** (ADR 0099, `apps/api/src/automation-scripts/`) never runs in the API process. `runner.ts` is a process of its own, started with Node's permission model (it reads its own code, writes nowhere, opens no connection, starts nothing) and an empty environment; inside it the script runs in a QuickJS interpreter compiled to WebAssembly, with 64 MiB and 10 seconds, a minute for all the scripts of a run.
  - `sandbox.ts` starts that process, checks each message it sends, ends it at the time limit, and lets four scripts run at once. `host.ts` does what a script asks, with the public API's operations, as the automation's author and within the automation's base; a script's `fetch` is made there too (ADR 0101), as a webhook's call is (`requestPinned`, `webhooks.ts`), with the automation's secrets, sealed in its row and put in only for the host each is kept for. Off unless an administrator allowed it (`automationScripts`).
- **Notifications** store references only; names are read when listed, and those about tables the reader can no longer open are hidden.

### Imports, exports, and jobs

- **Imports** are read in a worker thread with a 512 MiB heap, so a hostile file costs one failed upload, not the API process (ADR 0025). The upload is written to disk as it arrives; a first pass (five minutes at most) finds its columns, counts its rows up to `IMPORT_MAX_ROWS`, and keeps a sample; the file is staged as it came, with what that pass found, for 30 minutes (`staged_uploads`), readable only by the uploader, and kept two hours once queued.
  - The job reads it again a batch of 500 rows at a time, each within a minute, and writes each batch while the next is read (ADR 0064). A spreadsheet's zip directory is checked before anything is inflated: at most 2,000 entries, 1 GiB each, 2 GiB in all.
- **A workbook made a base** (ADR 0078) is read the same way: a first pass in the worker reads every worksheet in turn, its header, its rows, its formulas, and each column's type from every row of its sheet (`FieldGuess`), and stages the file (`staged_uploads`, kind `workbook`) for its uploader, half an hour. The `import_workbook` job makes the base, a table of each chosen sheet, and writes each sheet as it reads it again, up to `IMPORT_MAX_ROWS` rows in all; a failure or a cancel removes the base.
- **Jobs**: imports, view exports, table copies, base snapshot export/import, and restore points are rows of the `jobs` table that people follow, each run by one graphile-worker job queued in the same transaction and tried once. Each API process runs `JOB_CONCURRENCY` (2) of them at a time, apart from the event work (`WORKER_CONCURRENCY`, 4). A running job renews a two-minute lease; a job whose lease lapses (its process died) is marked interrupted within a minute.
  - A job runs with its author's current rights, checked again when it starts. Progress goes to the author's own channel at most once a second, as counts only. A person may have five jobs queued or running. Cancelling stops a job at its next progress report; an import keeps the batches it already wrote, a partial copy is deleted.
- **A base snapshot** is a versioned document (`kind: anygriddb.base`, version 3, and version 4 for what the instance keeps for itself; ADRs 0039, 0076, 0117): tables and the folders they are kept in, columns, collaborative views, links with their direction and inverse field, lookups and rollups, members by email, and the base's dashboards, each widget naming its table by its key and its view by its rank (ADR 0108). Automations, webhooks, public links, comments, and the change trail stay with the base.
  - With data it is a `.zip` (up to 2 GiB; its JSON up to 40 MB) whose every table's rows are the lines of their own entry, `rows/<key>.ndjson`: cells, user cells by email, attachments by file, the row's sequence number and place, and the sequence numbers its links name; the attachments' files sit beside them. Rows are read a thousand at a time by sequence number and written 500 at a time, up to `EXPORT_MAX_ROWS` and `IMPORT_MAX_ROWS`. Schema-only export is the JSON alone.
  - Versions 1 and 2, their rows inside the JSON (100,000 at most), still import. Import always creates a new base: rows keep their sequence numbers and places, through which their links are made in bulk; people without matching members are reported and dropped from user cells.
- **A restore point** (ADR 0077) is a snapshot with its data kept in the files' store under `restore-points/<id>`, with its line in `restore_points`, for `restorePointDays` (30 by default), 20 per base at most. It and a base's copy are written in version 4 (ADR 0117): each row keeps its dates, authors, and status, a status coming back through the audited transitions and a signed row coming back locked, without its signature. A table copied with its rows keeps them the same way. A file from outside is never believed on any of that. Restoring one makes a new base beside the old: the members of then who are still in the base get their role back, with their own role and rules on each table, and the base's groups the role they have now. Snapshots with data carry each person's access to each table, by email, for that.
- **A link to a whole base** (`shares.base_id`, migration 0089; a share names a view or a base, never both) opens through `share.openBase` and `share.baseRows`: each live table of the base its creator reads, under their field and row rules, as a view's link reads under its creator's.
  - It writes nothing, lets nothing be copied, is never framed (its page is `/s/b/<token>`, outside a view link's frame rule), and keeps a view link's password, access proof, lock after ten wrong passwords, expiry, and the instance's rule for public links; attachments stay behind, as on every link. A link's password is given once, in a request's body (`share.unlock`, `share.unlockBase`), for the proof its readings then carry.
- **A base's activity** (`catalog.baseActivity`) is the change trail as a member reads it: the events of the tables they may read, each table's newest read through its `(table_id, occurred_at)` index and merged, a page of 50 by a cursor of the last event's instant, to the microsecond, and id.
  - A table where a row rule keeps rows from them is left out, as the home page leaves out its last change; a field hidden from them is left out of an edit, and an edit of hidden fields alone is not told; a table's fields made with it are told by its creation. Field names only, and a row by its primary field as the reader reads it now: values stay in the row's history.
- **Access and structure on the trail.** What gives access to a base or sends its data out is on the change trail too (trigger `audit_catalog`, migration 0091): public links, invitations, webhooks, automations, and the members of a group, beside the tables, fields, links, roles, rules, feeds, and sources it kept already.
  - Each such event names the catalog table it changed (`audit_events.catalog_table`), which is how Administration's trail says a public link from an invitation; events written before name none. No secret enters the trail, hashed or sealed, nor the address an invitation was sent to: the trail outlives an account's erasure, and an invitation taken becomes a role, which names its account.
  - A webhook's counters of failed deliveries and its sealed values are not events: a change of the encryption key rewrites those and changes nothing a person set. Making or revoking an API token is on the sign-in trail (`token_created`, `tokens_revoked`).
  - A write to one of these tables outside `withAudit` is refused ("Audit context required"); a write nobody asked for (a webhook switched off after too many failed deliveries) is made under the name of who made the thing, with the source `worker`. The structure of a base is there as well (migration 0092): the base itself, the views everyone shares, dashboards and their widgets, and folders.
  - What only arranges the screen leaves no event (the order of views and folders, where a widget sits), nor does a person's own view, which nobody else reads. An event that is no table's names its base in Administration's trail, read from the row it kept. When an identity provider ends an account's sessions or tokens (SCIM), the sign-in trail says so, with the method `scim`. A base's activity shows none of these events: it describes rows, fields, and tables only.
- **Export and snapshot files** are kept under `exports/<job id>` and can be downloaded by their author for 24 hours. Snapshot uploads are staged for 30 minutes (two hours once the import job claims them). The hourly purge deletes expired staged uploads and export files.

### Files

- **Attachments**: the MIME type comes from the bytes; images get a WebP thumbnail; downloads check the reader's rights and send `nosniff`.
- **Files** (ADR 0010) go through one `FileStore`: a directory by default (`STORAGE_PATH`, writes land in a temporary file, are synced, then renamed), or any S3-compatible service (`STORAGE_DRIVER=s3`). Keys match one whitelist, so a key never becomes a path outside the store. An instance with `S3_*` set and no driver keeps using S3.
- **Orphaned files.** A file is stored before the row that names it. A daily sweep deletes files older than a day that no row names (an upload that died before its row), and the disk driver's leftover temporary files. A folder or a bucket therefore belongs to one instance, and a database restored from a backup should come with the files of the same moment: the sweep removes files only newer rows named.

### Administration

- **Instance controls** (ADR 0042, `apps/api/src/admin-control.ts`): `auth_events` keeps sign-ins, refusals, sign-outs, and what an administrator did to an account (ended sessions, removed factors, revoked tokens), with the account, the acting administrator, a method, a detail code, and the client address; never an email, a password, or a token.
  - A trigger keeps it append-only but for events past six months, the least an instance keeps (the hourly purge removes those older than the instance says, six months to a year), and for erasure, which clears the account's ids and addresses. Maintenance lets only administrators open a session or use a token (`instance_maintenance`, 503) and ends the others' sessions; an announcement shows above the app; the instance may require a second factor of every account. The gates read the settings through a five-second cache per process.
  - Administration also lists sessions and every person's jobs, failed deliveries, and pending invitations, exports both trails and an access report as CSV (formula-looking fields quoted), and builds a support bundle without data or secrets.
  - Administration decides who sees which base (ADR 0057): an administrator adds a person with roles on any live base, sends a pending invitation again or withdraws it, each grant on the change trail under their name; an account it creates has no password until its first link, valid a week, sets one. Deleting an account disables it first in the same transaction (ADR 0059).
- **The instance's identity** (ADR 0072): its name, a note on the sign-in pages, and its mail's sender name, signature, and invitation note are instance settings; its logo is the one row of `instance_logo`, set through `admin.setLogo` (PNG, JPEG, or WebP by its first bytes, 256 KiB) and served to anyone at `/api/instance/logo`, cached by its version. `InstanceMark` (`apps/web/components/brand/`) draws it wherever the product's mark was.
  - Every mail is written and sent with one `MailVoice` (`apps/api/src/mail-i18n.ts`, `readMailVoice`): the language, the name, the sender name, the signature; `sendMail` takes it as an argument.
- **An administrator's way into a base** (ADR 0074, `apps/api/src/data/emergency-access.ts`): `admin.baseOverview.open` keeps a row of `emergency_access` for an hour, with a reason; `sessionBindings` adds a viewer's role on the bases an administrator has open to their own session (pages, socket, the jobs they start), never to a token, an automation, a webhook, a feed, or a public link.
  - The opening is on the change trail (`access`), and `tellOwners` notifies the base's owners in the app and by mail; the same notice goes out when an administrator gives themselves a role, which asks a reason. Any other role an administrator gives on a base (to a person, at an account's creation, from a file, to a group, to a group's new member) is told to its owners in the app, one notice per gesture (`data/role-notices.ts`).
- **Handing over** (ADR 0075, `apps/api/src/data/handoff.ts`): `admin.handOver` gives the bases a person alone owns a second owner, moves the automations and webhooks they made where the successor may manage the table (they run with their author's rights), names those that stay, and revokes the person's API tokens when asked; the account is left as it is.
- **The proof** (ADR 0073): every change made in Administration asks for the password or the second factor again, unless one was given in the last five minutes (`sessions.stepped_up_at`). One rule, in the base procedure of Administration (`apps/api/src/trpc/admin-procedure.ts`), before the input is read: every mutation asks but those `proof-rule.ts` names with their reason. On the screens, `lib/proof.ts` asks the person and sends the refused change again; `ProofGate` is mounted once in Administration's shell.
- **Security policy** (ADR 0043): instance settings with defaults and floors (`POLICY_BOUNDS` in `packages/core/src/instance.ts`), each read on its own. `enrollmentGate` asks administrators for a second factor always, then owners or everyone as set; with `ssoMfa: "provider"` an account without a password counts as enrolled, an administrator never (ADR 0114).
  - `apps/api/src/auth/lockout.ts` counts failed passwords and codes per account (`users.failed_sign_ins`, `locked_at`) and refuses a locked account before checking its password; the lock's length is the policy's at the time of reading. `auth/password-reset.ts` keeps one-time links by hash (`password_resets`); a new password ends the account's sessions and lock and keeps its factors.
  - Session windows, token lifetimes (older tokens included), and public links follow the settings through the gate cache. After single sign-on an account with a factor goes through the second step (`/login?mfa=1`). `auth/security-mail.ts` tells the person of a lock, a new password, removed factors, and sends reset links.
- **Account policies** (ADR 0044): `authorize(ctx, true)` refuses base creation to non-administrators when kept to them, `findApiToken` ignores non-administrators' tokens when tokens are, and `assertMemberDomain` (`data/sharing.ts`) holds invitations, grants, and pending invitations to the sign-up domains when asked.
  - `users.active_at` moves at sign-in, token use, and re-enabling; the hourly purge runs `auth/inactivity.ts`, which warns once a week ahead (with email) and then disables idle accounts (`disabled_reason = 'inactive'`), never administrators or SCIM accounts. `auth/lock-alerts.ts` puts an `account_locked` notification in other administrators' bells and mails them, at most ten an hour, then one "many" alert.
- **Acting as a person** (ADR 0091, `apps/api/src/data/acting-as.ts`). An administrator, after the proof and with a reason, uses another person's rights for thirty minutes. The session stays the administrator's: the author of every change is the administrator, and `audit_events.impersonated_user_id` names the person. The sign-in trail records the start and the end, and the person is told, in the app and by mail.
  - Administration is closed while it lasts, except to stop it. An API token ignores it. Another administrator, a support account, an auditor, and a disabled account cannot be acted as.
- **The administration API** (ADR 0086, `apps/api/src/admin-api.ts`): `/api/v1/admin` lists and makes accounts, lists the invitations that wait, and reads and changes the settings of the instance's running, for an operator's scripts; `/api/v1/admin/openapi.json` describes it. Its tokens are made in Administration, each for the scopes it names, and work while their maker is an administrator. A token cannot give the proof: it makes no administrator, gives no role, and changes none of the settings that decide who gets in.
- **Sign-in events to a collector** (ADRs 0056, 0084, 0105; `apps/api/src/integrations/siem.ts`, `syslog.ts`). The events of the sign-in trail a watch cares about leave as they happen: posted as signed JSON over HTTPS, or as RFC 5424 lines to a syslog collector over TLS, its certificate verified. Both are set and tried in Administration. Each event leaves from the queue, is tried again when the collector is away, and carries ids, codes, and the client's address, never an email or a secret.
- **What the environment holds** (ADR 0083). Email, single sign-on, the largest attachment, and the syslog collector can be set where the instance is installed instead: Administration then shows them, without their secrets, and cannot change them.

### Operations

- **Observability** (ADR 0018, `apps/api/src/observability.ts`): Prometheus metrics on `/metrics` for the operator's token only, `METRICS_TOKEN` or the one set in Administration (404 without either): requests by route pattern, tRPC procedures, transactions and connections in use per client database, the pool every request goes through (connections open, idle, and waited for), background tasks, the job queue by state, failures pages report, and the process.
  - A page whose code fails in a browser tells its own instance (`POST /api/client-errors`, `apps/web/lib/report-failure.ts`): one log line and a counter, bounded, with no account and no session, and a secret address masked. `/health` says the process is up; `/ready` answers 503 while PostgreSQL does not answer within two seconds (`apps/api/src/readiness.ts`), for a load balancer or a monitor.
  - OpenTelemetry spans (requests, procedures, source transactions, tasks) go to `OTEL_EXPORTER_OTLP_ENDPOINT` over verified TLS when it is set; otherwise the SDK is not loaded. A log line keeps of an error its kind, its code, the constraint PostgreSQL names, and its frames, the same of its cause, and never its message: a message quotes what failed (an address a mail server refused, the row PostgreSQL would not take).
  - One serializer does it for every line (`apps/api/src/logged-error.ts`), the start's and the queue's included; a task that fails reaches the queue without its words.
- **Rate limits** per client address, counted in each process's memory: sign-in 20, the way to an identity provider and back (`/auth/`) 300, an application's token addresses (`/oauth/token`, `/oauth/revoke`) 120, public shares 240, REST, MCP, and SCIM 600, uploads 120 (attachments, imports, and a base's file), files sent to public forms 30, failure reports from pages 30, and the app 3,000 requests a minute. Behind a load balancer with several processes, each one counts its own share.
  - A request names one call that checks a password, a code or a secret link at most, and such calls about one account take turns, so that none is compared past the account's lock (ADR 0095); an application's token addresses are counted apart from people's sign-ins. A request carries a hundred calls at most.
- **Retention**: webhook deliveries and automation runs 30 days; notifications 90 days once read, 180 days otherwise; jobs 7 days; the sign-in trail six months to a year, as the instance says (a year by default); spent reset links a week; unanswered sign-ups a day; a session, an unfinished single sign-on attempt, and an unanswered second-step or passkey challenge until the hourly purge after they expire (`apps/api/src/auth/expired.ts`). The date of an account's last sign-in is its own (`users.last_sign_in_at`), so neither purge takes it away.
- **Start-up.** The API refuses to start without `DATABASE_URL` and a 32-byte `AUTH_ENCRYPTION_KEY`. `PUBLIC_URL` is the HTTPS origin people open (links in emails, cookies, API documents, the certificate's primary name, and the WebAuthn RP ID); it is HTTPS and defaults to `https://localhost:<PORT>`. Plain HTTP is accepted only on the loopback, for the development server.
  - Passkeys need a DNS hostname (or `localhost`) there; an IP alone keeps HTTPS and TOTP (`TLS_NAMES` covers extra certificate SANs only). Optional: `STORAGE_PATH` or S3, SMTP, OIDC, SAML, `ATTACHMENT_MAX_BYTES`, `ADMIN_EMAILS`, and `DATABASE_POOL_MAX` (the connections requests share, 10 by default).
- **Migrations** (`packages/db/src/migrate.ts`). Plain SQL files in `packages/db/migrations`, applied in order when the API starts, under an advisory lock, so two processes starting at once do not both migrate. A server older than PostgreSQL 16 is refused before anything is written (`PostgresTooOld`). A migration that may refuse a database, for data it cannot keep, carries `NNNN_name.check.sql` beside it: every pending migration's check is asked, read-only, before the first one runs, so an upgrade that is refused changes nothing, and the version before starts again (`UpgradeRefused`, ADR 0106).

## Sources

- **A source** is a client database AnyGridDB reads (ADRs 0006, 0026); [`docs/sources.md`](docs/sources.md) is the DBA's guide. Only instance administrators declare one, on a host the operator allows (`ANYGRIDDB_SOURCES_ALLOWED_HOSTS`: names, `*.` domains, addresses, ranges; empty allows none).
- **Connection.** It signs in with a dedicated account, over TLS with the certificate verified: the administrator may paste the server's certificate authority or its self-signed certificate, and nothing turns verification off. Only the operator's development flag `ANYGRIDDB_SOURCES_ALLOW_PLAINTEXT` connects without TLS, and the administration page then says so. A PostgreSQL superuser is refused. Every connection is named `AnyGridDB` for the DBA's monitoring.
- **Saving, and the engines.** A source is saved only once a connection succeeded. Its password is encrypted with `AUTH_ENCRYPTION_KEY`, never sent back, and never logged; the audit trail records a change of password by its date.
  - Engines:
    - PostgreSQL 13 or later.
    - MySQL 8.0.16 and MariaDB 10.6 or later (`mysql2`), declared, checked, and introspected, their tables exposed and read.
    - SQL Server 2017 or later (`tedious`), its tables exposed and read through a T-SQL dialect, formulas, lookups, and rollups included: the compiler follows each number's T-SQL `decimal(p, s)` (`packages/core/src/query/digits.ts`) so results stay exact where the declared types allow, and marks the field where they may be rounded.
    - Oracle Database 19c or later (`oracledb`, thin mode, no Oracle client in the image), its tables exposed, read, and written like the others; what its engine does differently (an empty text is NULL, `NUMBER` keeps no scale) is listed in [`docs/sources.md`](docs/sources.md) and under Known limits in the roadmap.
  - On Oracle, a DBA or SYSDBA session is refused. On SQL Server, a sysadmin or an account with CONTROL SERVER is refused. A MySQL or MariaDB server must have its time zone tables (CONVERT_TZ with named zones). On MySQL and MariaDB, an account with a global grant beyond rows (ALL, SUPER, CREATE USER, a `*_ADMIN` privilege, DDL on every schema, or the grant option) is an administrator and refused, and the server must be the engine chosen.
- **Exposing tables.** An administrator exposes tables of a source in a base; nothing is exposed by default. The catalog records a `storage = 'external'` table with its source, schema, name, and primary key (`data_tables.external_*`), and each client column under its own name and type (`physical_name`, `external_type`). A one-column foreign key to another exposed table becomes a link field, with its inverse on the target. AnyGridDB never runs DDL on a client table: purging one only forgets it.
- **Reads.** Rows stay in the client's database. The read engine compiles the same SQL for both kinds of table through `packages/core/src/query/storage.ts`: a client row is named by its key as text, has no system columns, and each client column reads in its field's SQL type (an enumeration or a `uuid` as text, an integer as `numeric`, a `timestamp` without time zone in the source's time zone, UTC by default).
  - Reads run on a pool per source (`apps/api/src/sources/pools.ts`), at most the source's connection limit, each in a read-only transaction under its time limit. A table or column the client dropped reads as `source_schema_changed`.
  - A client table read whole shows the total its engine's statistics estimate past 10,000 rows (`pg_class.reltuples`, `information_schema.tables.table_rows`, `sys.partitions`), counted exactly on demand; a count past the time limit falls back to the estimate, and only a view's first page asks for the total.
- **One read engine, several SQL dialects** (ADR 0005): `packages/core/src/query/dialect.ts` renders what engines spell differently.
  - Where an engine computes a function differently (floating point, SQL Server's 38 digits), the formula runs the engine's way and the field carries a limit (`packages/core/src/query/limits.ts`, ADR 0027), shown in its header and in the formula editor; only what no engine function can produce is refused (`function_unavailable`), which leaves an IANA zone CLDR does not map for SQL Server.
  - Lists (lookups) are ordered JSON outside PostgreSQL: ARRAY_JOIN, ARRAY_UNIQUE (first occurrence), ARRAY_COMPACT, SUM, MIN, MAX, and COUNTA read them value by value (JSON_TABLE, through a derived table on MySQL, whose JSON_TABLE cannot read a correlated subquery; OPENJSON on SQL Server), and a lookup of a list reads flat. A footer median is exact on every engine (ROW_NUMBER, not PERCENTILE_CONT). A compiled formula is bounded in size (`formula_too_large`).
  - A value read many times is bound once: in a derived table on MySQL, through JSON_TABLE on MariaDB, whose derived tables cannot see the outer row. MySQL and MariaDB sessions run with ANSI_QUOTES, PIPES_AS_CONCAT, and NO_BACKSLASH_ESCAPES, so identifiers, `||`, and literals read as in PostgreSQL; values are bound in server-side prepared statements, the driver turning `$n` into `?`; a result row comes back as one JSON object.
  - Link lists and lookups are built with GROUP_CONCAT (ordered) as JSON text, their joined text computed beside them, and searched with JSON_SEARCH and JSON_CONTAINS: JSON_TABLE in a correlated EXISTS reads wrong on MySQL, and MariaDB hides TABLE_CONSTRAINTS from an account that only reads, so keys come from KEY_COLUMN_USAGE.
- **Writes.** An exposed table is read-only until an administrator enables its writes in the source (ADR 0028): editing, adding, and deleting each on their own (`external_table_read_only`, `external_insert_off`, `external_delete_off`). Its columns are the client's: AnyGridDB never changes them (`external_table_schema`). Formulas, lookups, rollups, and buttons may be added, since they store nothing, and fields of AnyGridDB's own are kept beside the table (ADRs 0032, 0046). Comments on a client's row live in the control plane, under its key.
- **Fields AnyGridDB adds to a client's table** (ADRs 0032, 0046) live in a side table of the source's side schema, joined on the key in the client's engine, or, without one, in `external_enrichment_values` (one JSON bag per row, by key); `data_columns.external_control_plane` records which, so naming a side schema later moves nothing.
  - Control-plane values are merged into a page after the client read (field rules applied); a view's filter on them resolves to key lists first (`sources/control-plane-read-filter.ts`, at most 1,000 rows), sort and group are refused (`control_plane_sort`), and any other filter on them is refused (`control_plane_filter`) rather than compiled against an empty value. Their writes lock the bags in AnyGridDB's database across the client's write and keep the three-step trail.
- **Read replica.** A source may name a read replica (`sources.replica_*`): `SourcePools.read` uses it and falls back to the primary when it is unreachable; writes stay on the primary. Its password is sealed like the primary's and kept out of the audit trail; empty, it is the primary's.
- **A store that speaks no SQL** is read from a copy, and only from a copy (ADR 0088): `apps/api/src/sources/copy/` holds one connector per store, which signs in, lists what the account may read, and reads a table's rows from first to last (`CopyConnector`); it builds no query from what a person asks.
  - Exposing a table makes its copy at once, empty, with a refresh queued (`startCopy`); the synced-table job (ADR 0034) fills it through the connector (`SourcePools.copyRows`), a thousand rows at a time and a million at most, and compares it with the copy before. Every read goes to the copy through the one read engine, so `ExternalRelation.dialect` is PostgreSQL for such a table.
  - A value that is not of its field's type reads empty and is counted (`fitCopyValue`, `external_syncs.left_out`). Nothing is written to the store: no write, no side schema, no replica (`source_copy_only`). The connection goes to the host the source names and no other.
  - The first store is a database that speaks the MongoDB wire protocol, tested against FerretDB; the second is OpenSearch, read through its REST API with Node's own HTTPS client (`copy/http.ts`), each request under the source's time limit as a whole, and no redirect followed.
- **A base held in a source.** A base may keep the tables it creates in a schema of a PostgreSQL, MySQL, MariaDB, or SQL Server source (ADR 0090): `bases.home_source_id` and `home_schema` name it, and the statements that create the schema, its tables and their columns, and drop them, are built in `packages/core/src/query/home.ts`, every name checked there.
  - Such a table is an external table whose schema AnyGridDB made (`isHomeTable`): a field that stores one value is a column of it, typed as a side column is, and its rows are read and written as a client's are. A field or a table deleted for good is dropped there; the schema is dropped only when an administrator types its name at the base's permanent delete (`apps/api/src/sources/host-table.ts`).
- **Incremental refresh.** A synced table may refresh incrementally: the rows past the change column's mark, found with the watch builders (`packages/core/src/query/watch.ts`), are read live and upserted into the copy; every `full_every` refreshes, and after any failed pass, the table is copied whole, which finds deletes and takes a new mark.

## Tests

- Unit tests (Vitest) sit beside the module they test, with an accepted and a refused case. Code that queries a database is tested in the integration suites instead of against fakes, and what people do on a screen in the journeys; so a router or a large component often has no test file of its own beside it.
- Testcontainers suites run the migrations and the read engine against PostgreSQL 18, and the conformance suite against PostgreSQL, MySQL, MariaDB, SQL Server, and Oracle.
- Playwright journeys in `apps/web/e2e`, one per flow rather than per view, each checked with axe (WCAG 2.2 A and AA).

## Ops

```bash
cd docker && docker compose up -d --build
```

The stack is PostgreSQL and AnyGridDB, with files on the `files` volume. `compose.s3.yml` adds RustFS and moves files there.

Operator commands run in the API image as `anygriddb`: the first account's token, an administrator's way back in, the encryption keys, moving files between stores, a backup's report. [`docs/operations.md`](docs/operations.md) has each with its procedure.

See also the [decision records](docs/adr/README.md), the [migration plan](docs/history/migration-plan.md), which is history, and [`OPEN_SOURCE_POLICY.md`](OPEN_SOURCE_POLICY.md).
