# AnyGridDB architecture

The product is a Turborepo / pnpm workspace.

## Shape

```text
browser ──► one origin: the app (apps/web, built by Vite), tRPC,
              │          REST /api/v1, MCP /mcp, WebSocket, file routes
              ▼
           apps/api (Fastify) ── graphile-worker: row events, webhooks,
              │                   automations, notifications, schedules
              │                ── product jobs: imports, exports, copies, snapshots
     ┌────────┼──────────────┐
     ▼        ▼              ▼
 packages/  packages/db    file store: a directory (default) or any S3
 core       (Kysely, pg)   attachments, thumbnails, exports, staged uploads
              │
              ▼
         PostgreSQL 18 ─── one physical table per user table, the catalog,
                           the job queue, realtime (LISTEN/NOTIFY), locks
```

| Package         | Job                                                                                                                |
| --------------- | ------------------------------------------------------------------------------------------------------------------ |
| `apps/web`      | Single-page app: typed routes, virtualized grid, views, dashboards, record panel, settings, admin                  |
| `apps/api`      | Sessions, tRPC routers, REST API, MCP server, row services, attachments, import and export, WebSocket hub, workers |
| `packages/core` | Field types and configs, SQL builders with bound parameters, formulas, filters, RBAC, Zod input schemas            |
| `packages/db`   | Kysely client on `pg`, plain SQL migrations and their runner, catalog types generated from the database            |
| `packages/ui`   | Tailwind tokens (light and dark) and shared components                                                             |
| `docker/`       | The only install path                                                                                              |

## Data model

- A user table is a PostgreSQL table named by `physical_name`. Each has `id`, `ag_status`, and system columns `ag_seq`, `ag_created_at`, `ag_updated_at`, `ag_created_by`, `ag_updated_by`, filled by the `ag_stamp()` trigger, and `ag_position`, the row's place in the table's order: rows are read by place, then by sequence, and a row put between two others takes a number between theirs (ADR 0060).
- Columns have a stable `name` (the physical column and the API key) and a `label` shown to people. Links are a foreign key, with its index (one-to-many), or a junction table (many-to-many); a two-way link adds an inverse column on the other table that shares the same storage.
- Formulas, lookups, rollups, link labels, and buttons have no physical column. The read engine in `packages/core/src/query` compiles the page payload into one bound query (`buildReadRows`), so they filter, sort, group, and aggregate in that SELECT. Counts, group stacks, footer aggregates, and comment badges are separate bound queries on purpose. A computed field over a table the reader cannot read compiles to null. Formulas mean the same on every engine (ADR 0005), held by the conformance suite (`apps/api/src/sources/conformance.integration.test.ts`): computed numbers are exact and read canonical (`14.5`), division and AVERAGE round to 20 decimals, text compares by code point, and instants add and subtract in UTC, the reader's zone applying where a formula reads a wall clock. Formulas read text as a date by AnyGridDB's grammar, the same on every engine (ADR 0005): ISO 8601, a date with an optional time and zone (`Z`, `±HH`, `±HH:MM`); text without a zone is in the reader's time zone, and anything else, a day that does not exist included, is blank.
- Every row write runs in `withAudit`: one transaction that sets `anygrid.user_id`, `anygrid.table_id`, the reason, and the source. The `audit_record()` trigger appends the old and new row to `audit_events`, refuses changes to `locked` or `signed` rows, and enforces the status workflow. `audit_events` and `row_signatures` are append-only.
- Sources in the audit trail: `web`, `api`, `import`, `template`, `duplicate`, `restore`, `trash`, `form:<share>`, `snapshot`, and `automation:<id>`.
- Trash: deleting a base, table, field, or view sets its `deleted_at` and keeps its storage. Every catalog read goes through the `live*` predicates in `apps/api/src/data/live.ts`, so the item disappears everywhere: sidebar, engine, REST, shares, realtime channels, schedules. A table takes the link fields of other tables that point to it into the trash (`deleted_with`), and a two-way link takes its other side; they come back with it. A field read by a formula, lookup, or rollup cannot be deleted, and one that would not compile cannot be restored. A trashed field keeps its name, so a new field gets another one, and views keep their references to it: reads leave them out, a restore brings them back. A restored table or field whose name was taken meanwhile becomes "Name (2)". After the days the instance keeps them (`trashDays`, 30 by default, a week to a year), a daily system job purges the item for good, audited under whoever deleted it; managers can purge earlier.

## Contracts

- The API serves the built app on its own origin (ADR 0011): every call from the browser is a relative URL, so there is no CORS, the session cookie is first-party, and nothing about the address is fixed at build time. Page paths get `index.html` with `script-src 'self'` and `connect-src 'self'` (no inline script, no nonce); hashed files under `/assets` are cached for a year, and go out as the Brotli or gzip copy the build left beside them; any other answer of 1 KiB or more is compressed as it leaves (`apps/api/src/compression.ts`), request bodies never unpacked; share and invitation pages carry `noindex`, and never the name of what they share. In development, Vite serves the app and forwards the API's paths to it, so the browser sees one origin there too.
- Dialogs, popovers, menus, and tooltips are React Aria Components (ADR 0012), in `packages/ui`: focus moves into an overlay and back to its trigger, the page behind a modal is inert, menus take arrow keys and type-ahead, and a tooltip's trigger must be focusable. Two things keep the browser's own `title` instead: text that is cut short or only decorates (a file name, a status, a fingerprint), which nothing can focus, and a control drawn once per cell or per pin, where a tooltip each would cost the grid its speed. Kanban cards move between columns by mouse or from the keyboard, with a drag handle; calendar events by mouse, or by editing the date.
- Messages (ADR 0013, source language ADR 0041) are Lingui macros with **English** as the source language; `pnpm --filter @anygriddb/web i18n:extract` writes the PO catalogs in `apps/web/locales`, and CI fails when they lag behind the code or French translations are incomplete. A language loads its catalog when it is chosen, before the first render. Server errors are translated from their code (`apps/web/lib/errors.ts`); values the server sends, such as webhook outcomes, row statuses, and template names, from a closed list (`lib/known-text.ts`). System mail uses `apps/api/src/mail-i18n.ts` with the instance locale.
- The grid is a DOM grid with the ARIA grid pattern (ADR 0012): focus stays on the grid, which names its active cell with `aria-activedescendant`; cells carry their row and column indexes, `aria-selected`, and `aria-readonly`; numbers are row headers. The selection (active cell, range, edited cell, fill) lives in a store outside React state (`components/grid/selection.ts`); each cell reads only its own flags, so moving the selection re-renders the cells whose look changes, not the grid. Rows load into another external store (`use-rows.ts`), page by page as they scroll. A grouped grid's first page also says where each group starts (`buildGroupCounts` with `starts`, which numbers the view's rows in the read's own order), so its headers are placed before the rows under them are read (`group-layout.ts`); a grouped read orders rows whose group values sort alike by their key, so each group's rows follow each other. A gallery reads its cards the same way, page by page as they scroll; a map reads only the rows that have a place, up to 5,000 (`map-places.ts`). A view setting is read first with its value kept locally, then saved: the rows read stay as long as what the read asks for is the same (`readKey`).
- The formula editor is CodeMirror 6 on the parser the server runs (`packages/core/src/formula.ts`): it highlights the tokens, completes `{fields}` and functions with their arity, and underlines a parse error where it is, with the message also in a status line a screen reader hears. The server checks the types when the field is saved. The editor's code loads with the first formula.
- Routes are typed (TanStack Router): a link to a page that does not exist, or a search parameter of the wrong shape, is a compile error. Each page loads its own code. The React Compiler memoizes components; its lint rules run in CI, so a component it would skip is an error, not a silent slowdown.

- tRPC is the TypeScript contract; Zod schemas live in `packages/core`.
- Errors (ADR 0013): every error people may read is an `AppError` from `packages/core/src/errors.ts`, with a stable code, an optional detail (a field, a function), its HTTP status, and an English message. tRPC sends `{ code, detail }` in `data.reason`; REST, file routes, and job records carry `code` and `detail` next to the English `error`. Anything else is internal: the client learns `internal_error` and the log keeps the cause. The web app translates the code, never the message.
- Exact numbers (ADR 0023): a number field, and every computed number (formula, lookup, rollup, sum, mean, extreme), travels as a canonical decimal string, in the grid, REST, webhooks, and exports, so no value rounds through a float. Ratings, durations, and auto numbers stay JSON numbers. Typecast keeps the digits that were typed; a JSON number is accepted and read as the decimal it prints as. Display formats the string with `Intl.NumberFormat`, which reads it exactly; only charts and map pins convert to a float.
- Row writes go through `apps/api/src/services/rows.ts`, whatever the transport: tRPC, REST, MCP, automations, public forms (ADR 0022). The service checks writable fields, rows in scope, link targets (an inverse one-to-many link needs write access to the other table), attachment ownership, and change reasons, then announces the change once. Transports parse input and present results; they hold no write logic. Rows that set the same fields are inserted in one statement, in their order, and the rows of an update are locked together, in the order of their ids.
- Writes to a client's table (ADR 0028) go through the same service, then `apps/api/src/sources/writes.ts`: enabled per table (edit, add, delete) by an administrator, each column per the account's rights. Rows are locked, read again, and compared with what the writer saw; statements come from `packages/core/src/query/external-write.ts`, in each engine's types. Each write is recorded in `external_writes` and `external_write_steps` (intent, applied, confirmed), append-only; the `external_settle` job confirms and settles them.
- Synced tables (ADR 0034, `apps/api/src/sources/sync.ts`, `packages/core/src/query/sync.ts`): a copy in the `ag_sync` schema of AnyGridDB's database, refreshed by the `external_sync` job, which pages through the client's table, loads a new copy beside the current one, compares them by `ag_id` (the row's id from the client's engine), and swaps them by renaming in one transaction. The engine reads a synced table as PostgreSQL (`ExternalRelation.synced`); `storeOf` keeps every join in one database, so a link between a copy and a live table reads empty. Writes are refused; a copy is dropped a minute after the table is read live again.
- Statuses on a client's rows (ADR 0033, `apps/api/src/sources/statuses.ts`) live in `external_statuses`, named by the row's key, with the same workflow and roles as `ag_status`. Locking seals the row: its stored fields in a canonical form (`packages/core/src/query/seal.ts`) and their SHA-256. A write reads the row's status before anything and again once its intent is recorded; a lock commits the status, waits for the writes recorded before it, then reads the row, so no write lands unsealed. The `external_seals` job (every five minutes, and at once for the rows a watch finds changed) compares sealed rows with the client's database, marks and notifies a change (`row_changed`), and records it. `external_status_events` is the append-only trail; `row_signatures` records the fingerprint signed.
- HTTPS only (ADR 0029, `apps/api/src/tls/`): the operator's certificate (`TLS_CERT_FILE`, `TLS_KEY_FILE`, reloaded when the files change), or one from the instance's own authority in `TLS_DIR`: ECDSA P-256, name-constrained to the instance's names, keys sealed with `AUTH_ENCRYPTION_KEY`, the server certificate renewed a month before it ends. The first byte of a connection tells TLS from plain HTTP, which gets a redirect on the same port. `/tls/authority.crt` serves the authority to install; Administration > Health shows its fingerprint.
- Connections AnyGridDB opens (ADR 0030): TLS, verified, beyond the loopback; `readEnv` refuses a `DATABASE_URL`, `S3_ENDPOINT`, or `SAML_ENTRY_POINT` that would not be, and SMTP requires TLS. The compose stack's one-shot `certs` service (`anygriddb tls services`) issues PostgreSQL and RustFS their certificates from the instance's internal authority, name-constrained to their names; PostgreSQL's `pg_hba.conf` takes network connections over TLS only.
- Observability (ADR 0018, `apps/api/src/observability.ts`): Prometheus metrics on `/metrics` for the operator's `METRICS_TOKEN` only (404 without one): requests by route pattern, tRPC procedures, transactions and connections in use per client database, the pool every request goes through (connections open, idle, and waited for), background tasks, the job queue by state, failures pages report, and the process. A page whose code fails in a browser tells its own instance (`POST /api/client-errors`, `apps/web/lib/report-failure.ts`): one log line and a counter, bounded, with no account and no session, and a secret address masked. `/health` says the process is up; `/ready` answers 503 while PostgreSQL does not answer within two seconds (`apps/api/src/readiness.ts`), for a load balancer or a monitor. OpenTelemetry spans (requests, procedures, source transactions, tasks) go to `OTEL_EXPORTER_OTLP_ENDPOINT` over verified TLS when it is set; otherwise the SDK is not loaded. A log line keeps of an error its kind, its code, the constraint PostgreSQL names, and its frames, the same of its cause, and never its message: a message quotes what failed (an address a mail server refused, the row PostgreSQL would not take). One serializer does it for every line (`apps/api/src/logged-error.ts`), the start's and the queue's included; a task that fails reaches the queue without its words.
- Session cookie: `__Host-`, `HttpOnly`, `Secure`, `SameSite=Strict`. A session slides by its idle window while used and ends at its lifetime: 15 minutes and 12 hours by default, as the instance sets them (ADR 0043). Every sign-in path goes through `createSession`, which refuses disabled accounts.
- Passwords: Argon2id, 64 MiB. Past the instance's first account, a password sign-up makes no account until its address is proved (ADR 0058): `signup_requests` keeps it and a link is mailed to the address; the account is made when the link is opened with the same password, or at once from an invitation to that address. Every account's address is thus proved, and what trusts an address (`ADMIN_EMAILS`, a role by address, SSO and SCIM matching) needs no check of its own. TOTP secrets: AES-256-GCM. Passkeys: WebAuthn. Deleting one's own account asks the proof a sensitive action asks (`apps/api/src/auth/erase-proof.ts`): the password, a code from the authenticator or a backup code when the account has one, and, where neither can be asked (no password, or a passkey for only factor), a sign-in less than ten minutes old. A wrong one counts toward the lock, a locked account takes no guess, and an API token is refused. Creating or administering a base needs a second factor.
- OIDC goes through `openid-client`: an HTTPS issuer whose metadata names itself, PKCE, a nonce, and a state kept server-side, used once, and taken only from the browser that started the sign-in (a `__Host-` cookie whose hash the state keeps; SAML's relay state likewise). A sign-on binds the account to the provider's subject (`sso_identities`: OIDC `sub`, a persistent SAML NameID) and later finds it by that subject, whatever the address says. The first time, the address finds the account: one the provider marks unverified is refused, and so is a different subject bringing the address of an account already bound to that issuer (`auth/sso.ts`). A SAML provider that sends only transient or address NameIDs keeps matching by address.
- Roles: owner, editor, commenter, viewer. A table role overrides the base role. A role given to an address is an invitation, whether or not the address has an account, and the answer is the same in both cases, so that inviting an address does not tell who has an account. An account's address being proved (ADR 0058), its holder finds the invitation on their home page and accepts or declines it there (`listInvitationsFor`, `answerInvitation` in `apps/api/src/data/sharing.ts`); an address without an account opens the mailed link. Only someone already in the base changes role at once. API tokens carry an optional base list and a read-only flag; the effective right is the lower of the token's and the user's.
- Field and row rules: `table_acls` and `column_acls` restrict a collaborator below their role; owners ignore them. With column rules, a field they do not name is hidden, so a field added later stays hidden until a manager opens it. Every read on behalf of a person builds its engine with `readerEngine` (`apps/api/src/data/acl.ts`), and the read engine enforces the rules wherever a table is read: a hidden field compiles to empty in the page, formulas, lookups and rollups from other tables, filters, sorts, search, groups, and aggregates, and is left out of responses and the catalog; a row rule is AND-ed into every read of its table, links and rollups included, and reads the real values even of fields the reader cannot see. A rule that no longer compiles keeps no row. This covers the grid, REST, exports, dashboards, webhook payloads, automations, and public shares (which read as their creator). Writes must name writable fields and target rows inside the rule (updates, deletes, links on both sides, statuses, signatures, comments, history). Collaborators with rules cannot use the row trash. An import that updates by key under a row rule updates the rows inside it and refuses, on its line, a key that finds a row outside it. Rule changes are audited like roles; revoking a member removes their rules. `catalog.viewAs` shows a manager what one collaborator reads, through the same engine.
- REST: `/api/v1` with record batches of 100, `typecast`, field keys by name or label, and `/bases/:id/openapi.json`. It takes a token, or the session on this origin (the API page tries requests with it).
- MCP (ADR 0040): Streamable HTTP at `/mcp`, stateless, a bearer token only (never the session), a browser's request from another origin refused. Its tools are the REST record plane; both read and write through `apps/api/src/public-api/`. A read-only token is offered the reading tools only. No language model is embedded.
- Realtime (ADR 0009): clients subscribe to table, base, and their own user channel. Messages carry row ids, never values; clients re-read with their own rights, once for a burst of changes. Each socket's messages are handled in order. The hub keeps the sockets of each channel, so a message goes to its channel's sockets without looking at the others. A socket is closed (4401) when its session ends: when it next speaks, and, for one that sends nothing, at the heartbeat, which asks in one query which of the open sockets' sessions are still live. Processes share messages through PostgreSQL `LISTEN/NOTIFY` on one channel: messages published in the same tick go out in one statement, each under PostgreSQL's 8,000-byte limit (row ids in chunks of 150). The listening connection reconnects on its own; tabs subscribed meanwhile get a `stale` message and re-read. A tab also re-reads each channel after its own link was lost, once subscribed again (ADR 0049); the server pings every socket every 25 s and cuts the silent ones, and a tab that hears nothing for 65 s opens a new link. Cell edit marks and button presses take short leases in the `ephemeral_locks` table (unlogged: a crash clears them, which is what a lease wants).
- Events (ADR 0008): a row write queues one graphile-worker job, `row_events`, inside its own transaction, so an event exists if and only if the write committed. The job reads the transaction's audit entries (`audit_events.xact_id`) and hands each row event to the consumers its table has, one job each, added in one statement: webhooks (an active one), assignment notifications (a user field that notifies), automations (one switched on). A table with none queues nothing more. Each consumer commits its own outcome with the jobs it starts (deliveries and their attempts, filter state and automation runs), so a retried job never sends twice. An import sends one `import` event: each batch replaces the queued event with its running count. Bulk catalog writes (field conversions, copies, templates, snapshots) send no row events. Realtime notices go out after commit and are not part of this guarantee.
- Webhooks: payloads may include the row's values, read with the creator's current rights. Deliveries are logged, retried after 1, 5, and 30 minutes (each attempt is a job keyed by delivery and attempt number), and a webhook switches off after 10 failures in a row. A sweep every ten minutes queues again a pending delivery whose attempt is long overdue. Outgoing requests check the resolved address inside the socket's own DNS lookup, so private and internal addresses are refused even under DNS rebinding.
- Automations run as their author, with the author's current rights, and audit their writes with the automation's name as the reason. They ignore their own writes, stop at depth 3, and run at most 300 times a minute each, counted from their recorded runs so the limit holds across processes. A run is a job tried once: actions send mail and call URLs. Schedules run from graphile-worker's crontab every minute and are claimed with `FOR UPDATE SKIP LOCKED`.
- Notifications store references only; names are read when listed, and those about tables the reader can no longer open are hidden.
- Attachments: the MIME type comes from the bytes; images get a WebP thumbnail; downloads check the reader's rights and send `nosniff`.
- Imports are parsed in a worker thread with a 512 MiB heap and a one-minute limit, so a hostile file costs one failed upload, not the API process (ADR 0025). A spreadsheet's zip directory is checked before anything is inflated: at most 2,000 entries, 256 MiB each, 512 MiB in all. Parsed files are staged in the file store for 30 minutes (`staged_uploads`), readable only by the uploader, and kept two hours once queued. XLSX is streamed and stops at 100,000 rows.
- Jobs: imports, view exports, table copies, and base snapshot export/import are rows of the `jobs` table that people follow, each run by one graphile-worker job queued in the same transaction and tried once. Each API process runs `JOB_CONCURRENCY` (2) of them at a time, apart from the event work (`WORKER_CONCURRENCY`, 4). A running job renews a two-minute lease; a job whose lease lapses (its process died) is marked interrupted within a minute. A job runs with its author's current rights, checked again when it starts. Progress goes to the author's own channel at most once a second, as counts only. A person may have five jobs queued or running. Cancelling stops a job at its next progress report; an import keeps the batches it already wrote, a partial copy is deleted.
- Files (ADR 0010) go through one `FileStore`: a directory by default (`STORAGE_PATH`, writes land in a temporary file, are synced, then renamed), or any S3-compatible service (`STORAGE_DRIVER=s3`). Keys match one whitelist, so a key never becomes a path outside the store. An instance with `S3_*` set and no driver keeps using S3.
- Export and snapshot files are kept under `exports/<job id>` and can be downloaded by their author for 24 hours. Snapshot uploads are staged for 30 minutes (two hours once the import job claims them). The hourly purge deletes expired staged uploads and export files.
- A file is stored before the row that names it. A daily sweep deletes files older than a day that no row names (an upload that died before its row), and the disk driver's leftover temporary files. A folder or a bucket therefore belongs to one instance, and a database restored from a backup should come with the files of the same moment: the sweep removes files only newer rows named.
- A base snapshot is a versioned document (`kind: anygriddb.base`, version 2; ADR 0039): tables, columns, collaborative views, optional rows (capped at 100,000), links with their direction and inverse field, lookups and rollups, user cells by email, and attachments in a `.zip` with the JSON (up to 2 GiB; JSON alone up to 40 MB). Schema-only export omits rows and files. Import always creates a new base; people without matching members are reported and dropped from user cells.
- A deleted row keeps its many-to-many links, from every junction it sits in (its own links, and links from other tables that point to it), in an internal audit event written in the delete's transaction (`__ag_m2m`, hidden from row history). Restore rewrites them for rows that still exist; an older event from an earlier deletion is ignored.
- Dashboards belong to a base. Widgets are `metric` (one aggregate), `chart` (one aggregate per group of up to two fields, from the read engine's `buildGroupAggregates`, drawn with ECharts in `components/dashboards/chart-view.tsx`, ADR 0035), or `view_embed` (link into a collaborative view). Data is read with the caller's rights, field and row rules included, and optional view filters.
- Rate limits per client address, counted in each process's memory: sign-in 20, public shares 240, REST, MCP, and SCIM 600, uploads 120, failure reports from pages 30, and the app 3,000 requests a minute. Behind a load balancer with several processes, each one counts its own share.
- Retention: webhook deliveries and automation runs 30 days; notifications 90 days once read, 180 days otherwise; jobs 7 days; the sign-in trail six months to a year, as the instance says (a year by default); spent reset links a week; unanswered sign-ups a day; a session, an unfinished single sign-on attempt, and an unanswered second-step or passkey challenge until the hourly purge after they expire (`apps/api/src/auth/expired.ts`). The date of an account's last sign-in is its own (`users.last_sign_in_at`), so neither purge takes it away.
- Instance controls (ADR 0042, `apps/api/src/admin-control.ts`): `auth_events` keeps sign-ins, refusals, sign-outs, and what an administrator did to an account (ended sessions, removed factors, revoked tokens), with the account, the acting administrator, a method, a detail code, and the client address; never an email, a password, or a token. A trigger keeps it append-only but for events past a year (the hourly purge) and for erasure, which clears the account's ids and addresses. Maintenance lets only administrators open a session or use a token (`instance_maintenance`, 503) and ends the others' sessions; an announcement shows above the app; the instance may require a second factor of every account. The gates read the settings through a five-second cache per process. Administration also lists sessions and every person's jobs, failed deliveries, and pending invitations, exports both trails and an access report as CSV (formula-looking fields quoted), and builds a support bundle without data or secrets. Administration decides who sees which base (ADR 0057): an administrator adds a person with roles on any live base, sends a pending invitation again or withdraws it, each grant on the change trail under their name; an account it creates has no password until its first link, valid a week, sets one. Deleting an account disables it first in the same transaction (ADR 0059).
- Security policy (ADR 0043): instance settings with defaults and floors (`POLICY_BOUNDS` in `packages/core/src/instance.ts`), each read on its own. `enrollmentGate` asks administrators for a second factor always, then owners or everyone as set; with `ssoMfa: "provider"` an account without a password counts as enrolled. `apps/api/src/auth/lockout.ts` counts failed passwords and codes per account (`users.failed_sign_ins`, `locked_at`) and refuses a locked account before checking its password; the lock's length is the policy's at the time of reading. `auth/password-reset.ts` keeps one-time links by hash (`password_resets`); a new password ends the account's sessions and lock and keeps its factors. Session windows, token lifetimes (older tokens included), and public links follow the settings through the gate cache. After single sign-on an account with a factor goes through the second step (`/login?mfa=1`). `auth/security-mail.ts` tells the person of a lock, a new password, removed factors, and sends reset links.
- Account policies (ADR 0044): `authorize(ctx, true)` refuses base creation to non-administrators when kept to them, `findApiToken` ignores non-administrators' tokens when tokens are, and `assertMemberDomain` (`data/sharing.ts`) holds invitations, grants, and pending invitations to the sign-up domains when asked. `users.active_at` moves at sign-in, token use, and re-enabling; the hourly purge runs `auth/inactivity.ts`, which warns once a week ahead (with email) and then disables idle accounts (`disabled_reason = 'inactive'`), never administrators or SCIM accounts. `auth/lock-alerts.ts` puts an `account_locked` notification in other administrators' bells and mails them, at most ten an hour, then one "many" alert.
- The API refuses to start without `DATABASE_URL` and a 32-byte `AUTH_ENCRYPTION_KEY`. `PUBLIC_URL` is the HTTPS origin people open (links in emails, cookies, API documents, the certificate's primary name, and the WebAuthn RP ID); it is HTTPS, defaults to `https://localhost:<PORT>`, and `WEB_ORIGIN` is still read in its place. Plain HTTP is accepted only on the loopback, for the development server. Passkeys need a DNS hostname (or `localhost`) there; an IP alone keeps HTTPS and TOTP (`TLS_NAMES` covers extra certificate SANs only). Optional: `STORAGE_PATH` or S3, SMTP, OIDC, SAML, `ATTACHMENT_MAX_BYTES`, `ADMIN_EMAILS`, and `DATABASE_POOL_MAX` (the connections requests share, 10 by default).

## Sources

- A source is a client database AnyGridDB reads (ADRs 0006, 0026); [`docs/sources.md`](docs/sources.md) is the DBA's guide. Only instance administrators declare one, on a host the operator allows (`ANYGRIDDB_SOURCES_ALLOWED_HOSTS`: names, `*.` domains, addresses, ranges; empty allows none).
- It signs in with a dedicated account, over TLS with the certificate verified: the administrator may paste the server's certificate authority or its self-signed certificate, and nothing turns verification off. Only the operator's development flag `ANYGRIDDB_SOURCES_ALLOW_PLAINTEXT` connects without TLS, and the administration page then says so. A PostgreSQL superuser is refused. Every connection is named `AnyGridDB` for the DBA's monitoring.
- A source is saved only once a connection succeeded. Its password is encrypted with `AUTH_ENCRYPTION_KEY`, never sent back, and never logged; the audit trail records a change of password by its date. Engines: PostgreSQL 13 or later; MySQL 8.0.14 and MariaDB 10.6 or later (`mysql2`), declared, checked, and introspected, their tables exposed and read; SQL Server 2017 or later (`tedious`), its tables exposed and read through a T-SQL dialect, formulas, lookups, and rollups included: the compiler follows each number's T-SQL `decimal(p, s)` (`packages/core/src/query/digits.ts`) so results stay exact where the declared types allow, and marks the field where they may be rounded; Oracle Database 19c or later (`oracledb`, thin mode, no Oracle client in the image), its tables exposed, read, and written like the others; what its engine does differently (an empty text is NULL, `NUMBER` keeps no scale) is listed in [`docs/sources.md`](docs/sources.md) and under Known limits in the roadmap. On Oracle, a DBA or SYSDBA session is refused. On SQL Server, a sysadmin or an account with CONTROL SERVER is refused. A MySQL or MariaDB server must have its time zone tables (CONVERT_TZ with named zones). On MySQL and MariaDB, an account with a global grant beyond rows (ALL, SUPER, CREATE USER, a `*_ADMIN` privilege, DDL on every schema, or the grant option) is an administrator and refused, and the server must be the engine chosen.
- An administrator exposes tables of a source in a base; nothing is exposed by default. The catalog records a `storage = 'external'` table with its source, schema, name, and primary key (`data_tables.external_*`), and each client column under its own name and type (`physical_name`, `external_type`). A one-column foreign key to another exposed table becomes a link field, with its inverse on the target. AnyGridDB never runs DDL on a client table: purging one only forgets it.
- Rows stay in the client's database. The read engine compiles the same SQL for both kinds of table through `packages/core/src/query/storage.ts`: a client row is named by its key as text, has no system columns, and each client column reads in its field's SQL type (an enumeration or a `uuid` as text, an integer as `numeric`, a `timestamp` without time zone in the source's time zone, UTC by default). Reads run on a pool per source (`apps/api/src/sources/pools.ts`), at most the source's connection limit, each in a read-only transaction under its time limit. A table or column the client dropped reads as `source_schema_changed`. A client table read whole shows the total its engine's statistics estimate past 10,000 rows (`pg_class.reltuples`, `information_schema.tables.table_rows`, `sys.partitions`), counted exactly on demand; a count past the time limit falls back to the estimate, and only a view's first page asks for the total.
- One read engine, several SQL dialects (ADR 0005): `packages/core/src/query/dialect.ts` renders what engines spell differently. Where an engine computes a function differently (floating point, SQL Server's 38 digits), the formula runs the engine's way and the field carries a limit (`packages/core/src/query/limits.ts`, ADR 0027), shown in its header and in the formula editor; only what no engine function can produce is refused (`function_unavailable`), which leaves an IANA zone CLDR does not map for SQL Server. Lists (lookups) are ordered JSON outside PostgreSQL: ARRAY_JOIN, ARRAY_UNIQUE (first occurrence), ARRAY_COMPACT, SUM, MIN, MAX, and COUNTA read them value by value (JSON_TABLE, through a derived table on MySQL, whose JSON_TABLE cannot read a correlated subquery; OPENJSON on SQL Server), and a lookup of a list reads flat. A footer median is exact on every engine (ROW_NUMBER, not PERCENTILE_CONT). A compiled formula is bounded in size (`formula_too_large`). A value read many times is bound once: in a derived table on MySQL, through JSON_TABLE on MariaDB, whose derived tables cannot see the outer row. MySQL and MariaDB sessions run with ANSI_QUOTES, PIPES_AS_CONCAT, and NO_BACKSLASH_ESCAPES, so identifiers, `||`, and literals read as in PostgreSQL; values are bound in server-side prepared statements, the driver turning `$n` into `?`; a result row comes back as one JSON object. Link lists and lookups are built with GROUP_CONCAT (ordered) as JSON text, their joined text computed beside them, and searched with JSON_SEARCH and JSON_CONTAINS: JSON_TABLE in a correlated EXISTS reads wrong on MySQL, and MariaDB hides TABLE_CONSTRAINTS from an account that only reads, so keys come from KEY_COLUMN_USAGE.
- An exposed table is read-only until an administrator enables its writes in the source (ADR 0028): editing, adding, and deleting each on their own (`external_table_read_only`, `external_insert_off`, `external_delete_off`). Its columns are the client's: AnyGridDB never changes them (`external_table_schema`). Formulas, lookups, rollups, and buttons may be added, since they store nothing, and fields of AnyGridDB's own are kept beside the table (ADRs 0032, 0046). Comments on a client's row live in the control plane, under its key.
- Fields AnyGridDB adds to a client's table (ADRs 0032, 0046) live in a side table of the source's side schema, joined on the key in the client's engine, or, without one, in `external_enrichment_values` (one JSON bag per row, by key); `data_columns.external_control_plane` records which, so naming a side schema later moves nothing. Control-plane values are merged into a page after the client read (field rules applied); a view's filter on them resolves to key lists first (`sources/control-plane-read-filter.ts`, at most 1,000 rows), sort and group are refused (`control_plane_sort`), and any other filter on them is refused (`control_plane_filter`) rather than compiled against an empty value. Their writes lock the bags in AnyGridDB's database across the client's write and keep the three-step trail.
- A source may name a read replica (`sources.replica_*`): `SourcePools.read` uses it and falls back to the primary when it is unreachable; writes stay on the primary. Its password is sealed like the primary's and kept out of the audit trail; empty, it is the primary's.
- A synced table may refresh incrementally: the rows past the change column's mark, found with the watch builders (`packages/core/src/query/watch.ts`), are read live and upserted into the copy; every `full_every` refreshes, and after any failed pass, the table is copied whole, which finds deletes and takes a new mark.

## Tests

- Unit tests (Vitest) sit beside the module they test, with an accepted and a refused case. Code that queries a database is tested in the integration suites instead of against fakes, and what people do on a screen in the journeys; so a router or a large component often has no test file of its own beside it.
- Testcontainers suites run the migrations and the read engine against PostgreSQL 18, and the conformance suite against PostgreSQL, MySQL, MariaDB, SQL Server, and Oracle.
- Playwright journeys in `apps/web/e2e`, one per flow rather than per view, each checked with axe (WCAG 2.2 A and AA).

## Ops

```bash
cd docker && docker compose up -d --build
```

The stack is PostgreSQL and AnyGridDB, with files on the `files` volume. `compose.s3.yml` adds RustFS and moves files there.

Operator commands run in the API image as `anygriddb`:

- `anygriddb storage migrate --from disk --to s3` (or back) streams every file the target lacks and deletes nothing. Run it, switch `STORAGE_DRIVER` and restart, then run it again for the files written meanwhile. `--dry-run` counts first.
- `anygriddb storage sweep --dry-run` lists the orphaned files the daily sweep would delete; without the flag it deletes them now. See the [decision records](docs/adr/README.md), the [migration plan](docs/migration-plan.md), and [`OPEN_SOURCE_POLICY.md`](OPEN_SOURCE_POLICY.md).
